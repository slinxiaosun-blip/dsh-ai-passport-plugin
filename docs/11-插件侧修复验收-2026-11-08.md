期望看到**时间戳是刚才**的两行：`module evaluated ...` 与 `apply {...}`。

## 前置（5 分钟）

1. DSH 桌面版已启动，插件已在 `desktop` profile 里（`~/.dsh/profiles/desktop/node_modules/dsh-ai-passport` 是软链）。
2. 设备开机、在广播；macOS 蓝牙已开。
3. 确认面板地址（默认 <http://127.0.0.1:19387/dsh-passport>，端口可能被占用或改过）：

```bash
lsof -nP -iTCP -sTCP:LISTEN | grep -iE "deepseek|dsh"     # 看实际端口
```

> ⚠️ 两个常见坑，别误判成插件坏了：
> - **curl 返回 502 却没有任何进程监听**：多半是 shell 里设了 `http_proxy`（国内很常见），
>   本地回环请求被送去代理了。加 `--noproxy '*'` 即可。
> - **面板打不开**：先确认 DSH 桌面版在跑。DSH 没启动时端口根本没人监听。

4. 记下三条基线命令，整个验收过程中反复用（都带 `--noproxy '*'`）：

```bash
B=http://127.0.0.1:19387/dsh-passport

# ① 链路全貌（最有用的一条）
curl -s --noproxy '*' $B/state.json | jq '{
  state: .state.link.state,
  device: .state.link.device.name,
  handshake: .state.link.handshakeComplete,
  lastDisconnect: .state.link.lastDisconnect,
  lastError: .state.link.lastError,
  reconnectAttempt: .state.link.reconnectAttempt,
  bridge: .state.diagnose
}'

# ② 桥进程（正常只有 1 个；卸载后应当 0 个）
pgrep -lf "bridge-worker.js"

# ③ 插件心跳日志（每次加载/失败都会写一行）
tail -5 ~/.dsh/dsh-ai-passport.log
```

5. 若设备是新刷的/换过机，需要先配对（**顺序别错**，打开串口会复位设备，配对码会变）：

```bash
B=http://127.0.0.1:19387/dsh-passport/action
post() { curl -s --noproxy '*' -X POST $B -H 'content-type: application/json' -d "$1"; }

post '{"action":"pair.unpair","payload":{}}' | jq -r .result.message
post '{"action":"device.connect","payload":{}}' | jq -r .result.message
# 立刻去看串口日志里的「配对码 (\d{6})」，10 秒内提交（XXXXXX 换成实际 6 位码）
post '{"action":"pair.submit","payload":{"code":"XXXXXX"}}' | jq -r .result.message
```

> `payload` 是必须的：动作参数一律放在 `payload` 里，平铺在顶层不生效。

## A. 工具注册（最高优先级）

以前这 4 个工具是**不存在**的（`tools.register()` 缺 `output` 直接抛错，被 catch 成一条 warn）。
所以"能调用"本身就是验收点。

| 验收点 | 操作 | 期望 |
| --- | --- | --- |
| A1 | 在 DSH 里对 agent 说：**「调用 ap_device_status」** | 工具能被调用并返回一个 JSON：`connected / state / device / firmware / battery / stats` |
| A2 | **「调用 ap_balance 查一下余额」** | `available:true` + `currency` / `totalBalance` / `rechargeBalance` / `bonusBalance`；未登录时返回 `available:false` + `reason`（不抛异常） |
| A3 | **「用 ap_device_notify 在设备上显示一句 你好」** | 设备屏幕弹出提示；工具返回成功 |
| A4 | 4 个工具都出现在工具列表/补全面板里 | 名称分别是 `ap_device_status`、`ap_device_notify`、`ap_device_ask`、`ap_balance` |

**不通过意味着**：工具注册又退化了。看 DSH 日志里有没有 `[passport] 工具注册失败`——
那条 warn 就是注册被拒的唯一痕迹，必须处理掉，不能带着跑。

## B. `ap_device_ask` 问答链路

设备端有一条硬约束：**题干只显示前 12 个字，每个选项 ≤ 10 个字**（更长的会被屏幕截断）。

| 验收点 | 操作 | 期望 |
| --- | --- | --- |
| B1 | 让 agent：**「用 ap_device_ask 问我：继续还是停止，选项 继续、停止」** | 设备弹选项页，两个选项都在；按上/下切换、按下键确认 |
| B2 | 在设备上选「继续」并确认 | 工具返回 `{"answered":true,"selectedIndex":0,"selected":"继续"}`；**设备页面自动收起** |
| B3 | 重来一次，在设备上取消作答（固件版式里有取消/返回入口时） | 返回 `{"answered":false,"reason":"用户在设备上没有作答（取消、超时或设备正忙）..."}` |
| B4 | 重来一次，让 agent 传 `timeoutSeconds: 10`，然后**什么都不按** | 约 10 秒后返回 `answered:false`；设备页面自动收起；**不会**卡住整轮对话 |
| B5 | 带 3 个以上选项（如 甲/乙/丙） | 三个都能显示、都能选中；`selectedIndex` 与所选项一致 |
| B6 | 只选「其他：语音输入」那一行说话 | 返回 `selectedIndex: -1` 且有 `custom` 字段（文本来自语音识别） |

> ⚠️ **选项文案不要重复**。设备只回传截断后的**标签文本**、不回下标，主机是按文本反查下标的；
> 两个选项写成一模一样的字，反查只会命中第一个。这是协议限制，不是 bug。
>
> 参数边界：`options` 最多 4 项、每项 ≤10 字（超长会被屏幕截断，别按"字数×字号"心算宽度）；
> 省略 `options` 时默认 `["确定","取消"]`；`timeoutSeconds` 默认 60、上限 300。

**不通过意味着**：要么设备侧协议对不上（看 `state.json` 的 `questionsTrace`），要么
`askOnDevice` 的分支走错。取 `questions` 字段 + `questionsTrace` 一起看。

## C. 链路状态机（4 条，重点是 C2 和 C4）

| 验收点 | 操作 | 期望 |
| --- | --- | --- |
| C1 | 正常连接一次 | `link.state = connected`、`handshakeComplete = true`、`device.name` 有值 |
| **C2** | 面板点「断开」→ 再点「连接」→ 连上后**把设备拿走/关掉电源** | 出现 `reconnecting`（退避 1s/2s/5s…），设备重新开机后**自动**连上。**这是旧版最狠的 bug：断开一次之后永不自动重连** |
| C3 | 翻日志守，不主动构造 | 若出现过 `heartbeat-timeout`，紧跟其后必须有重连；出现后停在 `idle` 就是没修好 |
| **C4** | 按住设备说话 5～10 秒 → 松开 → 等识别结果 | 识别完成后链路仍是 `connected`，`lastDisconnect` 不新增条目（旧版语音后有时自己掉线） |

C2 的细节：`state.json` 里 `link.lastDisconnect.reason` 会告诉你谁先动的手 ——
`peripheral-disconnect`（设备/系统层断）、`heartbeat-timeout`（主机判死）、
`bridge-exited`（桥进程没了）、`user`（你点的断开）。**验收时重点看这个字段对不对得上。**

这条以前会**卡死整轮对话**，务必验。

| 步骤 | 操作 | 期望 |
| --- | --- | --- |
| E1 | 让 agent 做一个需要审批的写操作（写文件 / 执行命令），配置里 `approval.enabled` 默认 true | 设备弹出审批页，电脑端同时出现审批卡片 |

正常应能看到 `链路断开，N 个待审批交回电脑端`。

## 2026-11-09 复测记录

### 1. 「其他」语音输入死循环（固件）

- 现象：单选页「其他」行单击进入语音页，按住说话、松手识别后自动弹回选择页，
  光标仍在「其他」行；再按确定又进语音页 —— 用户看到"按确认一直循环进语音输入"，
  主机始终收不到 `question.answer{submit}`，120s 超时后工具返回 `answered:false`。
- 修复：语音页改为**短按确定 = 确认**（<300ms，`ap_q_voice_is_tap`），识别结果
  留在语音页显示，不再自动弹回；单选确认时清掉预选草稿（custom 互斥），
  多选确认回选择页继续勾。`voice.error` 时语音页从"识别中…"复原，可直接重录。
- 验证：`ap_device_ask` 返回 `{answered:true, selectedIndex:-1, custom:"测试测试测试。"}`。

### 2. 设备总预选第一项（主机）

- 现象：`question.req` 的 `recommendedIndex` 用 `Math.max(0, findIndex(...))`，
  没有推荐项时被写成 0，设备把第一项预选成草稿；custom-only 的答案里混进
  「甲」，设备显示与回传下标对不上。
- 修复：主机改为直接下发 `findIndex`（无推荐 = -1）；固件解析缺省值也改为 -1。
- 验证：`device-ask.test.js` 断言 `recommendedIndex === -1`；真机 B6 回传 `selectedIndex:-1`。

### 3. 挂件与官方语音输入抢同一 single 槽位（插件 UI）

- 现象：两者都注册 `conversation.input.activity`（`kind: single`）。同时启用时
  第二个注册者激活失败，启动报 `web boot: 1 entry did not activate`
  （`@deepseek-ai/dsh-experimental-client-ui-voice-input: failed`），
  桌面端启动失败自愈还会把 profile 的 bundles 重置回 base + web-app。
- 修复：挂件改注册到 `conversation.input.left`（`kind: list`，同样提供
  `inputActions`/`useInput`），带自己的 `id: dsh-ai-passport`；弹层改为左对齐向右展开。
- 验证：两个 bundle 同时启用后，`input.activity` 占用者为官方语音输入、
  `input.left` 占用者为 `dsh-ai-passport-client`，均 active。
