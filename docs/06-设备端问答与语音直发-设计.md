## 1. DSH 侧契约（已逐一核实，出处为 DSH 内置包源码/文档）

### 1.1 输入框动词 `InputActions`（语音直发的地基）

`conversation.input.activity` 槽位的标准 props 含 `inputActions: InputActions`（同官方语音输入插件），
完整动词面（`SessionInputShell.actions`）：

```js
captureInsertion()          // 光标位置 + draftRev
insertText(text, span)      // 光标处插入；draftRev 冲突 / 提交中返回 false
setDraft(text)              // ★ 整段替换草稿
addAttachments / removeAttachment / pruneAttachments
submit()                    // ★ 提交（submit("queue")，排队模式）
```

另可读草稿内容：标准 props 的 `useInput: SnapshotSelectorHook<InputState>`（`inputState.draft`）。

- `insertText` 拒绝条件（返回 false）：`phase === 'adjudicating' | 'submitting'`，或 `span.draftRev !== rev`（用户在识别期间改过草稿）。
- **`submit()` 发送的是整个草稿**（不是"这段识别文本"）——这正是决策 1 选整段替换的原因：
  `setDraft(text)` 后草稿恰好等于识别文本，`submit()` 发出去的就是设备上确认的那句话。

### 1.2 提问/计划评审 `ctx.userQuestions`

| 事实 | 内容 |
|---|---|
| 数据形状 | `{callId, questions: [{id, question, detail?, header?, options:[{label, description?}], multiSelect?, intent?}]}` |
| 作答 | **一次性整批**：`{answers: [{id, selected: [label…], custom?}]}`，每题恰好一项；缺项报 `BAD_ANSWER` |
| Skip | 空 `{selected: []}` |
| custom 语义 | 多选：`selected` 与 `custom` 可共存；**单选：custom 互斥**（只交 custom，selected 为空） |
| 拦截通道 | host 侧瀑布 `ctx.on('user-questions/request', (request, next) => …)`（`ctx.waterfall("user-questions/request")` 已核实存在），与 `approval/request` 同构：返回答案对象即作答，`next()` 交回电脑端 |
| 超时题 | `askTimed` 到点变 *continued*，仍可补答：`ctx.userQuestions.answer(agent, callId, answer)`（host）或挂件 `ctx.remote.userQuestions.answer(sessionId, callId, answer)` |
| 错误码 | `BAD_ANSWER` / `REPLY_QUEUED`（已有回复在排队）/ `ASK_TIMED_OUT` / `ASK_CANCELLED` / `ASK_ABORTED` |

### 1.3 plan-review 的语义陷阱

`intent: {kind: 'plan-review', approve: '<批准选项 label>', callId?}` 的问题就是计划评审。
DSH 强校验：`approve` 必须是选项 label 之一；`detail` **必须**携带被评审的计划正文。

| 官方卡片动作 | 真实语义 | 设备端必须照抄 |
|---|---|---|
| **Approve** | 以 `intent.approve` label **作答**（`selected=[approveLabel]`） | 批准 = 作答 |
| **Request changes** | **不作答**，把等待拒绝成 `ASK_CANCELLED`，把用户带回输入框写修改意见 | 要求修改 = 交回取消，**不能**当成普通选项选进答案 |

  （[constants.js:171](../packages/dsh-ai-passport/lib/protocol/constants.js)、[app_proto.h:218](../vendor/ai-passport/main/app_proto.h)），
  设备端 [app.c:343](../vendor/ai-passport/main/app.c) 现为占位处理。

## 2. 语音直发（决策 1：整段替换 + 双击发送）

> 资产落位（模型缓存在哪、程序在哪、本条链路涉及哪些文件）见
> [04-桌面客户端集成](04-桌面客户端集成.md) 第七节；
> 录音归档（**默认开启**：落到挂件目录 + 自动清理最旧组，可配置关闭）见同节 7.5。

### 2.1 链路

```
设备 PTT 录音 → BLE → 主机识别 → voice.result{resultId, text} → 设备弹「识别结果卡」
   ├─ 单击确定 → voice.action{resultId, mode:'fill'}  → 挂件 insertText      → toast「已填入」
   ├─ 双击确定 → voice.action{resultId, mode:'send'}  → 挂件 setDraft+submit → toast「已发送」
   └─ 长按确定 → 放弃，重新录音（进 PTT）
```

主机侧：`VoiceDomain` 收到 `voice.action` 后把 `{resultId, text, mode}` 记入
`domainState.voice.pending`（state.json 暴露）；挂件轮询发现 pending 执行对应动词，
完成后 `POST /action {action:'voice.ack', payload:{resultId, ok, reason}}`；主机消费 pending（**一次性**，多窗口先到先得）并 toast 反馈设备。

### 2.2 识别结果卡（新覆盖页 `AP_SCREEN_VOICE`）

替代现在"只弹 toast"的呈现（toast 无交互、混在提示队列里会被挤掉——05 §9 缺陷 A 的教训）。

```
┌────────────────────────┐
│ 识别结果               │
│ 重构登录模块的鉴权层   │  文本区（上/下滚动，utf8_clamp 安全截断）
│ 并补一个 token 过期…   │
├────────────────────────┤
│ 单击填入 双击发送       │  底栏（只写做得到的事）
└────────────────────────┘
```

| 按键 | 行为 | 反馈（规范"成功/失败/加载"） |
|---|---|---|
| 上 / 下 | 滚动文本 | — |
| 单击确定 | 填入电脑输入框（`insertText`，**保留**草稿） | 「已填入」 |
| **双击确定** | **整段替换并发送**（`setDraft(text)` + `submit()`） | 「已发送」 |
| 长按确定 | 放弃，重新录音 | 「请重新说」 |

- 30 秒无操作自动收起，文本保留在挂件语音列表（可再手动填入）。
- 按键路由无 PTT 冲突：覆盖页打开时按键先被 `app_ui_handle_key` / `app_screens` 消费，PTT 只在主页生效。
- 单击会被 iot_button 压后一个双击窗口（~300ms）才触发，属双击语义的正常代价。

### 2.3 整段替换的风险与缓解（决策 1 的代价，明示记录）

**风险**：双击发送会**清掉用户在电脑输入框写了一半的内容**。用户已明确拍板接受
（"设备上看到什么就发什么"优先于"不碰草稿"）。

**缓解**：

1. 双击是显式动作（与单击区分），不是默认行为；
2. 单击仍走非破坏的 `insertText`，想保留草稿就用单击；
3. **旧草稿可找回**：挂件执行 `setDraft` 前把被替换的草稿存入 `domainState.voice.replacedDraft`
   （面板/挂件可见、可一键复制），"静默丢失"降级为"可找回"；
4. 危险操作仍受设备审批兜底，误识别直发不会绕过审批域。

### 2.4 失败面与降级

| 情况 | 行为 |
|---|---|
| 挂件不在（没开窗口/后台） | **2.5s** 无认领 → 降级 `sessionController.prompt({mode:'queue', content:[{type:'text',text}]})` 直发并 toast「已直接发送到任务」（`voice.fallbackPrompt` 配置，默认开）。★ 真机返工：窗口必须**大于**挂件 2s 轮询上界（旧值 800ms 会抢走近六成发送）；`content` 必须是**文本分部数组**（传纯字符串被严格校验拒绝 → 降级 100% 失败 → toast「发送失败」） |
| `insertText` / `setDraft` 报冲突（提交中） | toast「输入框忙，文本已保留」；文本留在语音列表 |
| `submit()` 执行时输入为空/被冻结 | 同上，记 debug 日志（此路径 DSH 未文档化，列为 spike） |
| 多窗口同时挂载挂件 | host pending 一次性消费；后到的 ack 返回 `ok:false`，不再执行 |
| 断链 | 卡片保留本地文本；重连后可重新操作 |

### 2.5 配置

```yaml
voice:
  directSend: true        # 识别结果卡 + 双击直发（取代旧 autoSend，旧项删除）
  fallbackPrompt: true    # 无挂件时降级 sessionController.prompt
```

## 3. 追问（单选 / 多选，含 custom 语音录入）

### 3.1 总体结构：主机持有整批真相，设备一次显示一题

2048B 单消息载荷、400KB SRAM、11 字/行的硬约束下，整批问题不可能一次下发、也不可能在设备上编辑批次。
因此：

- **主机**（新 `QuestionsDomain`）拦截瀑布请求后保存整批 + 已累计选择，**逐题**下发 `question.req`；
- **设备**只做"当前题的显示器 + 键盘"：勾选变化回发 `question.pick`，主机累计；
- 用户在设备上按「提交」→ `question.answer`（设备发"提交"信号）→ **主机组装完整 answers** 调瀑布返回；
- **任何异常都交回电脑端**：超时 / 断链 / 用户取消 → 主机 `next()`，绝不悬挂
  （延续审批域"设备无响应一律交回电脑端"的原则）。

### 3.2 追问页（新覆盖页 `AP_SCREEN_QUESTION`，复用审批页骨架）

```
┌────────────────────────┐
│ 问题 2/3        ▮▮▯▯▯ │  进度条
│ 选择要构建的目标平台？ │  题干（≤3 行，超长可滚）
│ [x] macOS             │  选项行：[ ]/[x] 复选标记
│ [ ] Windows           │  （单选显示 ( )/(•)）
│ [ ] Linux             │
│ ✎ 其他：说一句话…      │  custom 行（有内容时显示识别文本）
│ ▸ 下一题              │  动作行：下一题（最后一题变「▸ 提交」）
│   跳过此题            │
├────────────────────────┤
│ 上/下选择 ●确定勾选     │  底栏（随题型变化）
└────────────────────────┘
```

| 按键 | 单选题 | 多选题 |
|---|---|---|
| 上 / 下 | 光标移动（选项 + custom 行 + 动作行循环） | 同左 |
| 单击确定 | 选中并**自动进下一题**（对齐 DSH"单击即前进"） | **切换勾选** |
| 双击确定 | 提交整批 | 提交整批（快捷，等价走「▸ 提交」行按确定） |
| **长按确定** | **语音录入 custom**（PTT，松手识别） | 同左 |
| 光标在「跳过此题」按确定 | 本题 Skip（空 `{selected: []}`） | 同左 |
| 长按上键 | 取消整个提问，交回电脑端（`next()`） | 同左 |

细节约定：

- **Recommended 首选项预选为草稿**（对齐 DSH 语义：预选 ≠ 已提交）。
- 题干与 `detail` 合并在文本区，光标到边界时内部滚动。
- 提交整批时**未作答的题按 Skip 处理**（空 selected），与官方卡片 Skip 语义一致；
  底栏提示「还有 1 题未答」而不是禁用提交。
- 倒计时题复用审批页 `lv_bar` 倒计时；到点主机尝试 `answer()` 补交（见 §1.2），失败则 `next()`。
- 电脑端先答 → 设备提交收到已解决 / `REPLY_QUEUED` → toast「已在电脑上回答」并收起页（与 `approve.result` 同款）。

### 3.3 custom 语音录入（决策 2：进一期）

设备上打字不现实，而"说一句话"正是这台设备的强项。流程复用 05 的录音/识别管线：

```
长按确定（在某题下）→ PTT 录音（≤30s，松手收尾）→ 识别
→ custom 行显示识别文本（"✎ 其他：macOS 和 Linux 都要"）
→ 长按确定重录（清空）；照常参与单选/多选选择与提交
```

- 提交时按 DSH 语义打包：**多选** `selected + custom` 共存；**单选** custom 互斥（`selected: []` + `custom`）。
- 识别中/失败反馈复用 toast；录音期间状态推送抑制（`setDeviceRecording` 现有机制）。
- 与语音直发共用 `app_voice`，但**结果投递目标不同**：追问页内录制 → 写 custom 行；
  主页录制 → 识别结果卡。由"录制发起时的上下文"决定，互不串台。

### 3.4 消息

| 消息 | 方向 | 载荷 |
|---|---|---|
| `question.req` | Mac→设备 | `{callId, kind:'choice'\|'plan', index, total, qid, question, detail, options:"a\|b\|c", recommendedIndex, multiSelect:0\|1, approveLabel, hasCustom:0\|1, timeoutMs}`（**载荷拍平**：设备端 ap_json_* 只解析标量，选项用 `\|` 分隔；question≤40字/detail≤80字/选项≤5；单条 <1024B） |
| `question.nav` | 设备→Mac | `{callId, index}`（上/下一题；主机回 `question.req`） |
| `question.pick` | 设备→Mac | `{callId, qid, selected:[label…], custom?, skipped}`（增量，主机累计） |
| `question.answer` | 设备→Mac | `{callId, action:'submit'\|'cancel'\|'reject'}` —— **最终批由主机组装**；cancel=交回电脑端，reject=要求修改（拒绝等待 ASK_CANCELLED）（01 草案的 `{selected:[index]}` 载荷作废，以本文为准） |
| `question.done` | Mac→设备 | `{callId, ok, reason}` —— 提交被采纳/已在电脑上回答/超时，收起页面 |

## 4. 计划评审

### 4.1 评审页（`AP_SCREEN_PLAN`）

```
┌────────────────────────┐
│ 计划评审               │
│ 重构登录模块的鉴权层   │  计划标题
│ 1.提取Token校验中间件 │  detail 摘要（2-3 行）
│ 2.替换旧session…      │
├────────────────────────┤
│ ▸ 查看全文             │  进入翻页阅读（§4.3）
│   要求修改             │  一次确认即生效
│   批准计划             │  允许类 → 二次确认
└────────────────────────┘
```

| 按键 | 行为 |
|---|---|
| 上 / 下 | 光标在「查看全文 / 要求修改 / 批准计划」间移动 |
| 单击确定 | 查看全文 → 进阅读；要求修改 → 交回 `ASK_CANCELLED`；批准计划 → 进入待确认 |
| 双击确定 | 批准快捷（等价"选中 + 二次确认"一步完成） |
| （批准待确认态）再按确定 | 提交批准 `selected=[intent.approve]` |

- **确认成本不对称**（延续项目既定规则：拒绝一次确认、允许类二次确认）：
  底栏进入待确认态时写「再次按确定：批准」，一次误触不会直接放行。
- **要求修改 = 拒绝等待（ASK_CANCELLED）**，toast「请在电脑输入修改意见」——**不是**普通选项作答（§1.3 的语义陷阱）。
  实现注记：✅ 已验证可行——DSH `ask()` 的 catch 用 `restoreUserQuestionError` 按
  `{name:'UserQuestionError', code}` 形状恢复并抛出，宿主瀑布 answerer 抛该形状即拒绝等待。
  协议上与"取消"分开：`question.answer {action:'reject'}` = 要求修改（拒绝等待），
  `{action:'cancel'}` = 取消整个提问、交回电脑端（追问页长按上键）。
- 提交批准后设备显示「已批准」，随后 `task.state` 转运行中；主机回 `question.done` 收起。

### 4.2 与审批页的关系

- 同为"等人决定"，复用 `app_screens` 覆盖层骨架、倒计时条、"已提交，等待结果"反馈模式。
- 覆盖页优先级：**审批 > 计划评审 > 追问 > 余额**；同一时刻只显示一个，其余主机排队下发。
- `task.state` 优先级扩展为：`待确认（审批|追问|计划评审）> 运行中 > 已完成(8s) > 空闲`；
  提示音复用待审批双响（高-低急促），不新增音色。

### 4.3 全文翻页阅读（决策 3，**已于 2026-10-06 下线**）

> 本节描述的设备端阅读模式已整体删除（见 §9.3）。计划正文不再下发设备。

计划正文通常 1-2KB ≈ 小屏 10+ 屏，且单消息 2048B 装不下"题干 + 选项 + 全文"。
因此**主机分页、设备按需取页**（设备不持有全文，天然省内存）：

| 消息 | 方向 | 载荷 |
|---|---|---|
| `question.page.req` | 设备→Mac | `{callId, index}`（0 起，进阅读时先请求第 0 页） |
| `question.page` | Mac→设备 | `{callId, index, total, text}`（按约 500B/页切，UTF-8 边界安全） |

| 按键 | 行为 | 底栏提示 |

## 9. 2026-10-06 改版：电脑卡片与设备**同步显示**（竞速模型）+ 设备按钮化

### 9.1 背景：设备端再也收不到请求的真因

审批/追问长期"只在电脑上出现、设备毫无反应"。排查结论（有代码与实机证据）：

1. DSH 的审批/追问都是**回答者瀑布**：`ctx.waterfall(scopeTarget(agent…), "approval/request" | "user-questions/request", request, fallback)`；
2. cordis 的瀑布实现是 `next = () => (cbs.shift() ?? inner)(...args)` —— **监听者按注册顺序执行，谁不调 `next()` 谁截断整条链**；
3. 内置网页卡片在 DSH 启动时就注册了，**永远排在插件前面**：它一执行就弹卡片、等用户点击，
   插件的监听者根本轮不到（实测：拦截轨迹 0 条、设备端串口无任何 question 报文）。

**修法**：`ctx.on(..., { prepend: true })` 把设备监听者插到链首。修复后设备能收到请求了。

### 9.2 竞速模型：两边同时显示，先答者胜

用户要求"电脑卡片和设备同步显示"。旧模型（设备独占：不调 `next()`，设备不答才交回电脑）
本质是**串行**，改不成同步。新模型（`approval.js` / `questions.js`）：

```js
const card = this.#cardOutcome(next)        // ① next() 立刻调用 → 电脑卡片马上显示
const device = this.#startDeviceBatch(...)  // ② 同时推给设备 → 快捷按钮
const first = await Promise.race([card, device])   // 先答者胜
```

三个必须处理的细节：

| 细节 | 为什么 |
| --- | --- |
| **哨兵**：审批 `'unavailable'`/`undefined`、追问 `NO_PROVIDER` 视为"电脑端没参与" | 链尾兜底在没开窗口时会立刻返回哨兵；不忽略它，"只开设备"的场景会被秒杀 |
| **双向收尾**：电脑先答 → 发 `approve.result` / `question.done` 收起设备页；设备先答 → **主动中止下游 request 的 signal**，网页卡片随之自动收起（见 §9.6） | 否则另一边永远挂着 |
| **不阻塞**：设备超时/断链/取消只是"支线退出"，竞速继续等电脑卡片 | 设备不在线不该拖死正常审批流 |

### 9.3 设备端：一行极短摘要 + 快捷按钮（正文留在电脑卡片）

长题干/长选项在小屏上读不动（用户反馈）。设备退化成"实体遥控器"：

| 场景 | 设备显示 | 按键 |

| 计划待审 | 标题「计划待审」+ 一行摘要 + **要求修改 / 同意执行** | 单击确定即执行；**默认光标停在「同意执行」**；**无倒计时**；要求修改 = 拒绝等待（ASK_CANCELLED） |

设备端解析保留回退（`summary` 缺失时回退 `toolName`/`question`），旧主机仍可用。

### 9.6 设备先答后，电脑卡片为什么不消失（已修）

真机反馈："设备答完后，电脑上的卡片/审批弹窗没有收起。"

**机制**（读 DSH 客户端源码得到，不是猜的）：

1. 客户端 `answerQuestion` 用 **`request.signal`** 作为这次等待的生命周期
   （`AbortSignal.any([claimLifetime.signal, request.signal])`）；
2. 卡片的移除条件同时要求"**投影不再列它**"且"**自己的 request 已结束**"：
   ```js
   if (... || card.hasRequest() || card.pending.hasWaterfall()) continue;
   card.remove();
   ```
3. 竞速里我们**抢先返回**（设备先答）→ 下游那条 request 没有任何人结束它 →
   `hasRequest()` 永远为真 → 卡片永远留着。电脑先答时不存在这个问题
   （下游自己结束了自己）。

**修法**：在监听者入口把 `request.signal` **换成我们可控的 AbortController**
（原 signal 的中止仍然转发过去，不改变调用方的取消语义），设备胜出时
`lifetime.abort()` —— 下游 request 干净结束，卡片随之自动收起。审批域同款处理。

安全性说明：`ask()` / `approval.request()` 都在**进入瀑布之前**就把原 signal
存了局部变量（中止语义仍由原 signal 决定），我们替换的是下游监听者看到的引用；
我们返回的是值而不是抛错，服务端不会走 abort 分支。

回归钉子：追问域单测 + 接线集成测试各断言"设备胜出后 `request.signal.aborted === true`"。

### 9.8 真机事故：语音输入页说完话整机冻死（已修）

**现象**：进入「其他」→ 语音输入页 → 按住说话 → 说完之后**整机冻死**（只告警不复位，
屏幕定住，按键无响应）。

**现场**（串口）：

```
E task_wdt: Task watchdog got triggered ... - IDLE (CPU 0)
E task_wdt: Tasks currently running: CPU 0: app_task（表现上 app_voice 长跑不喂狗）
MEPC -> lv_inv_area（LVGL 刷新区失效逻辑）里死循环
I app_voice: 开始录音 session=2      ← 之后再无"录音结束"，52.2s 起系统整体静默
```

**根因（两个，同一类：非 LVGL 任务碰 LVGL）**：

1. **识别结果回调**（本轮新代码）：`app_question_on_voice_result()` 跑在 `app_task`，
   却直接调 `show_panel()` / `refresh_question_rows()` / `refresh_question_hint()`。
2. **录音收尾**（老代码，长期潜伏、被新页面踩爆）：`app_voice.c` 在录音结束时调用
   `app_ui_hide_toast()`，而它是**直接操作 LVGL** 的（`lv_obj_add_flag` +
   `lv_timer_delete`），`app_ui.c` 里没有任何 `bsp_lvgl_lock`。
   语音任务删 LVGL 定时器/改对象标志与 LVGL 任务并发 → 内部链表损坏 → 死循环。
   这解释了"卡在「录音结束」日志之前、PC 落在 LVGL、随后心跳也停"的全部现象
   （收尾正好是 VAD 静音判定那一刻，约开始后 2.5 秒）。

**真机验证（2026-10-06 修复后）**：连续 4 次录音全部"开始 → 正常结束"
（1940/1960/2480/2140ms），串口日志中 `task_wdt`/`Guru`/`MEPC` **出现 0 次**；
修复前是"开始录音 session=2"之后永不结束、7 秒后看门狗刷屏冻死。

**原始判断**：不是内存，也不是 LVGL 的 bug，而是**并发访问 LVGL**。
识别结果经链路消息队列送到 **app_task**，回调 `app_question_on_voice_result()`
里直接调了 `show_panel()` / `refresh_question_rows()` / `refresh_question_hint()`。
本仓库的线程模型是"LVGL 只允许在 LVGL 任务里用，其它任务必须持 `bsp_lvgl_lock()`
（按键路径就是这么做的）"——两个任务并发碰 LVGL，内部链表被破坏后死循环。

**修法**：两处都改成"只写结构 + 置脏标志，界面动作交给 LVGL 任务"——
回调走 `app_screens_tick_question() → consume_q_voice_result()`；
`app_ui_hide_toast()` 只置 `s_toast_hide_dirty`，由 `ui_tick` 里的 `toast_hide_now()` 落地
（同一轮里有新 toast 时以新 toast 为准）。
顺带修掉两处松手处理：**不再前置判断 `app_voice_recording()`**（快速点按时任务可能
还没醒，前置判断会漏掉这次停止，录音一路录到 VAD/上限 —— 主页 PTT 早就写明这条）。

**防复发**：新增静态门禁 `tests/test_lvgl_task_contract.py`（已接入 `validate.sh --static`）：

- **投递家族**（`app_ui_post_/set_/hide_/request_*`、全部 `app_screens_post_*`、
  `app_question_on_voice_result`，共 13 个接口）函数体内**不许出现 `lv_*` 调用**，
  也不许调用会碰界面的内部函数；
- **语音任务调用的每个 UI 接口**都必须在投递家族内（新加一个"直接碰界面的 UI 接口"就会失败）；
- 防空转断言：家族至少匹配到 10 个接口，否则这条契约等于没跑；
- 识别结果必须经 `s_q_voice_result_dirty` 标志投递，且 `app_screens_tick_question()` 必须消费它；
- `handle_key()` 必须先 `bsp_lvgl_lock` 再调 `app_ui_handle_key()`。

这条门禁做过**变异测试**：把 `lv_label_set_text(...)` 放回回调里，门禁立刻 FAIL。

**取证教训（同样重要）**：`vendor/ai-passport/build/*.elf` 可能是**旧产物**
（本次是 10 月 3 日的），真正与烧录镜像对应的 ELF 在 `build/firmware/<sha>/` 里。
用错 ELF 解析寄存器地址会得到完全错误的符号（当时误判成"LVGL 图像平铺绘制"）。
今后解 PC/backtrace：一律用归档目录里的 ELF。

### 9.9 日志降噪：迟到/重复 ACK（`app_link.c`）

语音突发期间音频通知会挤占控制通道，主机对**槽位已释放**的消息再回一条 ACK 很常见，
属于良性。但原实现每次都记一条 W（`ACK 未匹配任何在途消息`），一轮录音就刷一条 ——
把"日志里 0 个 E/W"这个长期使用的健康判据污染成"每条 W 都要人工判断"（排障时确实为此多花了一轮）。

**改法**（只动设备端，无协议变更）：加 `s_late_ack_count` 累计计数，
**首次记 W**（便于一次性确认），之后**每 20 次记一条**并带累计数，其余降 DEBUG。

**为什么不上报主机**：加 `lateAcks` 统计需要新协议字段与跨端改动，收益不抵成本；
"首次必记 + 累计数"已能兜住可观测性。

### 9.10 计时追问（askTimed）的设备端补答路径

**背景**：`ask_user_question` 有计时模式（正超时走 `askTimed()`，`-1` 走 `ask()`，见 asar 的消费者角色说明）。
倒计时结束后问题变成"继续追问"（continued）——**官方补答通道仍然开着**
（`userQuestions.answer(agent, callId, answer)`），但改版前的实现会立刻收掉设备页，
于是"设备上晚按几秒"就等于彻底失去作答机会。

**行为**（`lib/bridge/questions.js`）：

1. 识别可补答：`request.wait.timed === true` 且 `wait.callId` 非空，且卡片分支以
   `ASK_TIMED_OUT` 收场；
2. 不立刻收页：把 `pending` 标记为 `continued`，**重开一个补答窗口**
   （复用 `config.questions.timeoutMs`），设备页继续显示；
3. 设备提交后经 `ctx.get('userQuestions').answer(request.agent, waitCallId, { answers })` 投递；
4. **无论投递成败，本次瀑布仍以原来的 `ASK_TIMED_OUT` 结束** —— 工具侧语义保持
   `pending`（答案之后作为一条 user 消息进入会话），绝不把迟到答案当成瀑布返回值，
   那会和 `askTimed` 的既定语义打架；
5. 设备侧零改动：`question.done` 用既有字段表达结果，`ok=1` → 设备显示「已提交」，
   其余 reason 落「问题已结束」兜底。

**失败模式（全部 fail-safe，不重试、不猜测）**：

| 情况 | 处理 |
| --- | --- |
| `answer()` 抛 `REPLY_QUEUED`（已有一条回复在路上） | `ok=0, reason='answered-elsewhere'` + 收页 |
| `answer()` 抛 `BAD_ANSWER` | 记日志 + `ok=0, reason='rejected'` + 收页 |
| `userQuestions` 服务不可用 | 同今天：收页（`timed-out`） |
| 补答窗口内设备没答 / 断链 / 用户放弃 | 收页，不投递任何东西 |

**中止信号的歧义**：倒计时结束与"工具被调用方取消"会中止**同一个 signal**，两者现象一样、
后果相反（前者要保留补答窗口，后者要收页）。因此 abort 只记标记 + 起 300ms 宽限计时：
窗口内卡片报出 `ASK_TIMED_OUT` 就转成"继续追问"（并清掉该计时），否则按取消处理。

**回归钉子**：`questions.test.js` 三个用例（正常补答 / `REPLY_QUEUED` / 非计时题仍按原样收页）
+ `questions-voice-integration.test.js` 一条接线层用例（fake host 注入 `userQuestions`）。

### 9.11 手感观察：长按阈值 0.5 秒

真机验收时出现过两次"没打算提交却提交了"：设备上**按住确定 ≥0.5 秒**就会被判定为长按，
而长按在追问页的语义是"提交整批"。也就是说**用力按一下（而不是轻点）就会直接提交**。

- 这不是 bug（长按提交是用户明确要的出口，0.5s 是 BSP 既有阈值），但值得记下来；
- 若后续仍频繁误触，候选改法：把"长按提交"改成"双击提交"，或把追问页的长按阈值单独放宽到 1s。

### 9.13 系统设置页（阶段 B）

**覆盖层优先级**：设置页只是普通覆盖页之一 —— 审批/追问/余额/识别结果弹出时**优先显示它们**，
设置页被隐藏（`hide_all_panels()` 现在按屏枚举遍历，新增页面会自动纳入；原先硬编码列表漏了设置页，
导致审批弹出来时设置页还盖在上面）。

**入口与交互**：主页**长按上键**打开（该手势此前未占用）；上/下选择、**单击确定切换当前档位**、
**长按确定或长按上键退出**回主页。覆盖页打开时长按上键仍是"返回上一级"，不会误开设置。

| 项 | 档位 | 默认 |
| --- | --- | --- |
| 熄屏 | 常亮 / 1 / 2 / 5 / 10 分钟 | **常亮**（原来写死 5 分钟） |
| 自动休眠 | 不休眠 / 30 分钟 / 1 小时 / 2 小时 | **不休眠** |
| 提示音量 | 静音 / 低 / 中 / 高（0 / 40 / 70 / 100） | **中**（= 原来的 70，听感不变） |

**分层**（便于 host 测试）：
- `app_settings_logic.c`：纯逻辑 —— 档位表、`值 → 档位`（取最接近档，容错野值）、档位环状循环、
  `ap_settings_should_power_off()` 空闲判定。测试 `tests/test_settings_logic.c` 已接进 `validate.sh --static`。
- `app_settings.c`：NVS 持久化（命名空间 `apcfg`）——首次开机/键缺失/读失败回落默认值；值没变不写（省擦写）；
  写失败只记日志，本次开机内仍生效。
- `app_alert.c`：提示音带**音量**（`alert_get_volume/set_volume`）。静音 = 0 与旧的"关闭"等价，
  `alert_get_setting()` 保留为 `volume > 0`，主机下发的布尔配置仍兼容（开→中档、关→静音）。
  改音量档时**立刻试听一声**（调音量没反馈等于闭着眼调）。

**自动休眠的判定**（`ap_settings_should_power_off`）：任务运行中 / 覆盖页打开 / 正在录音，
**任一成立就不关** —— 审批等待中关机、说话说到一半关机都不可接受。空闲时长从
"最近一次按键或收到主机消息"算起。

**"休眠"怎么落地**：本板**没有软件可控的电源锁存引脚**（`bsp_pins.h` 里没有 PWR/LATCH），
所以"休眠"= 深睡（功耗降到最低：电量计/编解码/总线/屏幕全部挂起）+ **保证不会自己回来**：

- 休眠前写 NVS `pwr_off` 标记；开机早期 `auto_sleep_gate()` **按复位原因**判定：
  - **深睡唤醒 + 唤醒源是按键 + 开机瞬间按键确实按着** → 正常开机（清标记）；
  - 上电/外部复位（真断电、按复位键）→ 正常开机，不把人关在外面；
  - **USB 复位（`rst:0x15 USB_UART_CHIP_RESET`）、看门狗、软件复位等** → 重新睡回去。
- 另外两处"看起来像自己开机"的坑，真机定位后均已修：
  - **背光引脚**深睡时悬空会点亮屏幕 → 睡前拉低 + `gpio_hold_en` + `gpio_deep_sleep_hold_en`，
    开机早期释放 hold；
  - **唤醒引脚**（GPIO0）平时挂在 ADC 模式、数字输入通路关闭 → 深睡低电平唤醒被误判为"一直按下"，
    周期性自唤醒 → 睡前 `gpio_reset_pin` + 输入 + 数字上拉，交回普通 GPIO
    （C3 的 RTC IO 不支持方向/上下拉控制：`SOC_RTCIO_INPUT_OUTPUT_SUPPORTED=0`）。
- 用户可见的文案统一叫「自动休眠 / 唤醒」（不再叫"关机/深度休眠"）。

**关机动作**：复用深睡契约（顺序与 `demo_low_power` 一致）：
`bsp_battery_sleep` → `bsp_audio_sleep` → `bsp_audio_prepare_deep_sleep` → `bsp_i2c_prepare_deep_sleep`
→ 取 LVGL 锁 → `bsp_display_prepare_deep_sleep` → `esp_deep_sleep_start()`。
唤醒源为**按键**：三个键共用一个 ADC 分压节点（GPIO0），按下即拉低。
⚠️ 该唤醒方式**待真机确认**（见 docs/07 B4）；若第三键的分压电平（约 1.9V）落在数字判决门限附近导致唤不醒，
则自动休眠降级为"息屏待机"（背光关 + 任意键唤醒）。

### 9.14 配对（认领 / 信任握手，阶段 C）

**为什么放在应用层**：主机侧走 noble，macOS 的 BLE bonding/passkey 体验与成功率都差，
且换主机 / 换设备要反复配对。应用层握手复用同一条 GATT，跨平台一致。

**流程**（协议：`pair.begin` / `pair.ok` / `pair.failed` / `pair.required` / `pair.reset`）

1. 设备首次开机生成 16 字节密钥存 NVS（`apcfg.ps_secret`），并按
   `FNV-1a(secret ‖ 本次上电 nonce)` 派生 **6 位配对码** —— **每次上电都换新码**（防重放）。
2. 未配对期间设备**只接受** `hello` / `ping` / `pair.*`；其余业务消息一律回
   `pair.required`（**不执行**）。主机 hello 到达时设备把配对码页显示出来。
3. 用户在挂件里输入设备屏幕上的 6 位码 → 主机发 `pair.begin{code, host}`。
4. 设备校验：**常量时间比较** + **每分钟最多 3 次**（`app_pair_logic` 的纯函数，host 单测覆盖）。
   通过 → 随机生成 16 字节 token 存 NVS（`ps_token`），回 `pair.ok{deviceId, token}`；
   失败 → 回 `pair.failed{reason, remaining}`（`bad-code` / `rate-limited`）。
5. 之后主机每次 `hello` 带 `token`，设备校验通过（`ap_pair_host_token_ok`）才置位
   `s_host_token_ok` 并放行业务消息；不符/缺失则回 `pair.required{reason:"token"}`。
6. **解除配对**：主机发 `pair.reset` → 设备清 token 并**换新码**；主机侧删除信任记录。
   设备设置页也有「配对」行（未配对时可查看配对码）。

**主机侧**：`lib/bridge/pairing.js` 维护信任表 `~/.dsh/dsh-ai-passport.pairing.json`
（`{deviceId, token, name, pairedAt}`，权限 `0600`）；挂件在 `pairing.needed` 时显示
输入框 + 「配对」按钮，已配对时显示设备 ID + 「解除配对」。

**可移植性**：换新设备 → 新密钥 → 新码，配一次即可；换电脑 → 信任表不在，重配一次。
设备短 ID 由蓝牙 MAC 后 3 字节派生（主机信任表按它索引）。

**实现教训（真机踩到，已修）**
- 主机侧新增"域"必须实现约定的 `attach(runtime, ctx)` / `dispose()`；写成 `start()` / `stop()`
  框架不会报错、也**不会调用** —— 表现为"功能静默失效"（配对域就这么白跑了一轮）。
- 设备侧新增覆盖页要注意 `app_ui.c` 的"链路断开 → 覆盖层收回主页"逻辑；
  未配对时链路不会进 READY，配对码页必须**开例外**，否则用户看不到码。
- 挂件的过渡提示（动作返回消息）要在状态变化时清掉，否则会一直挂着骗人。

**安全边界（如实记录）**：码与 token 走**未加密**的 BLE 链路 —— 这是"认领/信任"机制
（防连错设备、防别人随手用你的设备），**不是**抗主动窃听的加密认证。
要更强保证的后续选项：把码升级为密钥协商（SPAKE2 一类），或启用 BLE 加密配对。
