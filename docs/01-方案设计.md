# AI Passport × DeepSeek Harness 联动方案

> 目标：把 AI Passport（ESP32-C3 掌上设备）做成 DeepSeek Harness（DSH）的**随身任务终端**——
> 在设备上新建/选择 DSH 任务、看执行状态、收完成提醒、做任务审批、看 DeepSeek 余额、用语音下指令；
> 设备与 Mac 之间走 **BLE 蓝牙**无线联机。

| 项 | 内容 |
| --- | --- |
| 编写日期 | 2026-10-02 |
| 目标硬件 | FoloToy AI Passport（ESP32-C3 / 8MB Flash / 无 PSRAM / 240×320 TFT / 三键 / ES8311 麦克风+喇叭） |
| 目标主机 | macOS（本项目开发机：Darwin arm64，macOS 27.0.1，Node v26.5.0 + DSH 内置 Node 24.21.0） |
| 宿主版本 | DeepSeek Harness 桌面版 0.2.0-rc.2 |
| 固件基线 | [FoloToy/ai-passport](https://gitee.com/FoloToy/ai-passport) `main @ 0b9e4c8` |
| 教程依据 | [用 AI Agent 创造专属玩法](https://ai-passport.folotoy.cn/guides/create-a-play-with-agent/)、[创造自己的玩法](https://ai-passport.folotoy.cn/guides/create-your-own-play/) |

## 1. 结论先行：三个关键判断

这一节是整份方案的地基，先把三个"必须说清楚、否则后面全错"的判断定下来。

### 判断一：蓝牙必须由**设备侧做外设（Peripheral）**

教程里的 `demo_ble.c` 只做广播，手机能扫到但连不上、也传不了数据。
要双向通信，必须由设备暴露一个 **NimBLE GATT 服务**（自定义 Service + 三条 Characteristic）。
Mac 侧做中央设备（Central）主动扫描连接。

反过来做（Mac 当外设）不可行：ESP32 侧做 Central 会与 Wi-Fi 抢占射频，且 macOS 的 GATT 服务端
在 Node 生态里几乎没有可用实现。

**结论**：设备 = BLE Peripheral（GATT Server），Mac = BLE Central。

### 判断二：语音识别**不能**放设备上，但 DSH 已经自带离线中文识别

ESP32-C3 无 PSRAM、单核 RISC-V，跑不动任何有意义的 ASR 模型。
所以语音链路的正确切法是：

```
设备 ES8311 麦克风录音 → 16kHz/16bit 单声道 PCM → BLE 分包上传 → Mac 侧识别 → 文本 → 注入 DSH 任务
```

**好消息（已实测确认）**：DSH 桌面版 `app.asar` 里**已经内置**完整的本地识别栈，只是默认没启用：

| 内置包 | 作用 |
| --- | --- |
| `@deepseek-ai/dsh-experimental-speech-to-text` | 提供 `ctx.speechToText` 注册表 |
| `@deepseek-ai/dsh-experimental-speech-to-text-sensevoice` | SenseVoiceSmall（中/英/日/韩/粤）**本地 CPU** 识别，int8 模型 239 MB |
| `@deepseek-ai/dsh-experimental-api-speech-to-text` | 把声音通过认证 Remote 暴露给浏览器 |
| `@deepseek-ai/dsh-experimental-voice-input-bundle` | 一键启用上面三个 + 麦克风 UI 的 bundle patch |

并且原生依赖 `sherpa-onnx-darwin-arm64`（含 `sherpa-onnx.node`、`libonnxruntime.dylib`）**已随包发布**，
本机是 Apple Silicon，**无需编译、无需 Python、无需联网即可离线识别**。

`voice-input-bundle` 的 patch 内容（已从 asar 中读出）：

```yaml
insert:
  - id: speech-to-text
    name: '@deepseek-ai/dsh-experimental-speech-to-text'
    config: { defaultProvider: sensevoice-local }
  - id: speech-to-text-sensevoice
    name: '@deepseek-ai/dsh-experimental-speech-to-text-sensevoice'
    config: { dataRoot: <DSH_HOME>/speech-to-text/sensevoice }
  - id: api-speech-to-text
    name: '@deepseek-ai/dsh-experimental-api-speech-to-text'
  - id: ui-voice-input
    name: '@deepseek-ai/dsh-experimental-client-ui-voice-input'
```

**结论**：启用该 bundle（或只启用前三个 host 包）→ 我们调用 `ctx.speechToText.transcribe()`。
**不需要**安装第三方 `dsh-voice-webspeech`——它走浏览器 Web Speech API，音频必须来自**浏览器麦克风**，
拿不到 BLE 传来的设备音频，帮不上忙（已读其源码确认：host 侧是空壳，不注册任何 provider）。

### 判断三：上位机的"应用"形态 = 插件自带本地 Web 控制面板

不做注入式挂件（依赖 DSH 前端内部结构，升级易碎），而是插件在 host 侧用 `ctx.webServer.register()`
起一组本地路由，提供**独立控制面板**：设备连接、任务列表、执行状态、审批、余额、语音，
全部在这一个页面里可视化。DSH 侧则通过插件事件/工具与它联动。

| 语音输入 | `ctx.speechToText.resolve()` + `transcribe(spec, signal)` → `Transcript.text` | 见 §5 |

## 3. BLE 协议设计

### 3.1 GATT 布局

| 项 | UUID（自定义 128 位） | 方向 | 属性 |
| --- | --- | --- | --- |
| Service | `0000a900-5041-5353-504f-5254a9000001` | — | Primary |
| `RX`（Mac→设备） | `…a901` | Mac → 设备 | Write Without Response |
| `TX`（设备→Mac） | `…a902` | 设备 → Mac | Notify |
| `VOICE`（设备→Mac） | `…a903` | 设备 → Mac | Notify（音频专用，避免与 JSON 抢队列） |
| `CTRL`（设备→Mac） | `…a904` | 设备 → Mac | Read（设备能力/版本/电量，连接后可立即读） |

广播名：`FoloPassport-DSH`；广播里带 Manufacturer Data（0xFFFF）标识 `protocolVersion` 与设备能力位，
便于 Mac 侧精准过滤，不用连上才知道是不是我们的设备。

### 3.2 帧格式

BLE 单包有效载荷受 MTU 限制（协商后约 244～512 字节），因此所有消息统一分片。

```
每片 = 4 字节头 + 载荷
  字节 0      : version(4bit) | flags(4bit)   flags: bit0=FIRST bit1=LAST bit2=ACK_REQ
  字节 1      : channel  0=JSON控制 1=音频 2=心跳 3=日志
  字节 2..3   : msgId(12bit) | seq(4bit)      用于乱序保护与去重
  载荷        : UTF-8 JSON 或 PCM 原始字节
```

- **重组**：接收端按 `msgId` 聚合，`FIRST` 开新消息，`LAST` 触发投递；`seq` 校验连续性，缺片则丢弃整条并请求重传。
- **可靠性**：控制通道消息要求 `ACK_REQ`，对端回 `{type:"ack", msgId}`；超时 400 ms 重传，3 次失败判链路异常。
- **音频通道**：不做重传（实时性优先），允许丢片；采用 **ADPCM（IMA/DVI 4:1 压缩）**把
  16 kHz/16 bit 单声道从 **32 KB/s 压到 8 KB/s**，配合 `libsodium` 级别的简单帧内冗余，稳定可用。
  如实测带宽紧张，退化为 8 kHz 采样（压后 4 KB/s），识别率对短指令影响可接受。
- **流控**：设备维护待发队列；`TX` 通知未确认时暂停取新数据，防止 BLE 栈溢出。
- **版本协商**：连接后 Mac 读 `CTRL`，双方以较小 `protocolVersion` 运行；不匹配时设备屏幕明确提示，
  而不是静默失败。

### 3.3 消息类型（JSON 控制通道）

设备 → Mac：

| type | 载荷要点 |
| --- | --- |
| `hello` | 固件版本、协议版本、能力位、电量、屏幕尺寸 |
| `task.list.req` | 请求任务列表（含 `limit`、`filter`） |
| `task.select` | `{sessionId}` 用户在设备上选中了某任务 |
| `task.new` | `{preset?, title?}` 请求新建任务 |
| `task.prompt` | `{sessionId, text, mode}` 把文本作为任务指令发送 |
| `task.cancel` | `{sessionId}` 中断（含设备端二次确认结果） |
| `voice.begin` / `voice.end` | `{sampleRate, format, durationMs}` 录音开始/结束 |
| `approve` | `{id, decision:'allow'\|'deny'\|'allow-always', scope:'once'\|'session'}` |
| `question.answer` | `{callId, selected:[index]}` |
| `balance.req` | 请求余额 |
| `ping` | 心跳，带设备 uptime 与 RSSI |

Mac → 设备：

| type | 载荷要点 |
| --- | --- |
| `hello.ack` | 主机名、DSH 版本、协议版本、当前工作区 |
| `task.list` | `[{id, title, status, running, updatedAt, progress, lastTool, errorSummary}]` |
| `task.detail` | 单任务展开：当前 step、正在跑的工具、最近一条助手文本摘要、耗时 |
| `task.status` | 增量状态推送（不重发整表，省带宽） |
| `task.done` | `{sessionId, ok, reason, summary, durationMs}` → 触发提醒 |
| `approve.req` | `{id, toolName, displayReason, risk, timeoutMs}` → 设备弹审批页 |
| `approve.result` | 审批结束（含超时/被网页端先答了）→ 设备收起页面 |
| `question.req` | 单选追问 |
| `balance` | `{currency, totalBalance, rechargeBalance, bonusBalance, todayUsed}` |
| `voice.result` | `{text, audioSeconds}` → 设备显示识别文本并等确认 |
| `voice.error` | 识别失败原因 |
| `toast` | 通用提示（如"任务已创建"） |

## 4. 设备端交互设计（全新 UI，不复用 demo）

上游规范明确要求：二次开发**必须重新设计并实现独立 UI**，禁止沿用 demo 测试菜单；
仅改名换色不算重设计。因此界面全部重做，采用"像素卡纸"风格延续品牌感但不复用 demo 布局。

### 4.1 首屏 · 任务台

```
┌──────────────────────────┐
│ ●DSH  ▮▮▮▯  ⌁87%        │  顶部状态条：连接、信号、电量
├──────────────────────────┤
│ ▸ 重构登录模块           │  选中项高亮（反色块）
│   RUN  · 2m14s · bash    │  运行中：状态胶囊 + 已耗时 + 当前工具
│                          │

│   DONE · 12:30           │
│                          │
│   调研向量库选型         │
│   ERR  · 09:14           │  失败：红色状态胶囊
│                          │
│   写周报                 │
│   IDLE · 昨天            │
├──────────────────────────┤
│ ▲▼ 选择   ●长按录音  ●新建│  底部键位提示（随上下文变化）
```

- **上/下短按**：移动选中项（长按连续滚动，带加速）
- **确定短按**：进入任务详情；在空列表时直接进入"新建任务"
- **确定长按**：开始录音（松手结束）→ 识别 → 作为该任务的指令发送
- **上键长按**：快速回到列表顶部 / 在详情页返回
- **下键长按**：拉取新任务列表 + 余额刷新

### 4.2 任务详情 · 执行状态

显示：任务标题、状态胶囊（IDLE/RUN/DONE/ERR/WAIT）、当前 step 号、正在跑的工具名、
最近一条助手输出摘要（截断到屏幕宽）、已耗时、可用操作提示。
运行中每 2 秒接收 `task.status` 增量更新，界面局部刷新（只重绘变动行，避免整屏闪烁）。

### 4.3 完成提醒

`turn/end` 到达时：

1. 屏幕顶部弹出 3 秒横幅：✅ 完成 / ⚠️ 出错 / ⏹ 已中断 + 任务名 + 耗时
2. 喇叭播放区分性提示音（成功：上行双音；失败：下行双音；中断：单短音）
3. 背光脉冲两次（在息屏/低亮度时也能察觉）
4. 未读任务在列表项右侧显示 ● 未读点，进入详情即清除

### 4.4 审批页（关键防误触设计）

```
┌──────────────────────────┐
│ ⚠ 需要你的授权           │
│                          │
│ 工具  bash               │
│ 原因  写入工作区文件      │
│                          │
│ 剩余 28s  ████████░░     │  倒计时进度条
│                          │
│  ▲ 允许一次              │
│  ▼ 拒绝                  │
│  确定 = 确认当前选择      │  二次确认，防误触
└──────────────────────────┘
```

- 审批请求带超时（沿用请求方 `signal`），倒计时归零自动按"拒绝"处理，绝不放行。
- 高风险工具（`bash`、`write`、`edit` 等）默认停在"拒绝"上，需要显式按上键切到"允许"。
- 无论走哪条路都在 DSH 侧留下审计事件（由 `approval` 服务负责），并同步到 Web 面板。

### 4.5 余额页

大字显示总余额（元），下方两行小字：充值余额 / 赠送余额，右下角"今日已用"。
数据来自 `deepseekAccount.getBalance()`；未登录或取不到时明确显示"未获取到余额"，
**不显示伪造的 0**（照抄 `dsh-whale-widget` 踩过的坑：错误不能缓存）。

### 4.6 录音页

实时电平条 + 已录时长 + 剩余可录时长；松手进入"识别中"动画；识别完成显示文本，
按确定 = 发送，按上/下 = 放弃。

### 4.7 中文字体（上游强制检查项）

AGENTS 明确警告：默认 Montserrat 字体**不含中文字形**，UTF-8 正确 + 编译成功都不代表能显示中文。
因此：任务标题、审批原因、"需要你的授权"等中文文本，必须先核对字形覆盖、
配置控件实际字体，并**在真机上做显示验收**（列为不可省的验收项）。

## 5. 语音链路详细设计

```
[设备] 长按确定
   └→ app_voice 启动：bsp_audio_set_format(16000,16,1) → bsp_audio_read 循环 20ms 分块
   └→ 本地 VAD 轻量门限（RMS）+ 最长 15s 上限 + 静音 1.2s 自动结束
   └→ IMA-ADPCM 压缩 → VOICE 通道分片 Notify
        ↓ BLE
[Mac] bridge/voice 按 msgId 重组 → 解码 ADPCM → 拼 WAV(16k/16bit/mono)
   └→ ctx.speechToText.resolve({ audio, language:'zh' })
   └→ ctx.speechToText.transcribe(spec, signal)  →  { text, audioSeconds }
        ↓
   └→ 回发 voice.result 给设备显示
   └→ 用户在设备上按确定 → task.prompt(sessionId, text, mode:'queue')
   └→ 或（免确认模式，可在面板里开）直接下发
```

要点与坑：

1. **provider 必须先就绪**。SenseVoice 首次使用要下载 239 MB int8 模型；插件应在面板上
   明确展示 provider 状态（用 `speechToText.snapshot()` 与 `prepare()`/`follow()`），
   未就绪时设备端显示"语音未就绪，请在电脑上准备模型"，而不是超时无响应。
2. **音频格式必须规范**。`api-speech-to-text` 会校验 WAV 头与时长上限（默认 `maxDurationSeconds: 120`），
   我们自己走服务层不受该限制，但仍按 16k/16bit/mono 规范生成。
3. **中文识别**：SenseVoice 支持 zh，`resolve({language:'zh'})` 明确指定，不用默认值赌。
4. **带宽实测**：ADPCM 4:1 后 8 KB/s，BLE 5 理论吞吐足够；但需真机实测丢包率，
   丢片率 > 5% 时降级到 8 kHz（4 KB/s）。

## 6. 上位机控制面板设计

插件用 `ctx.webServer.register()` 挂载在 `/dsh-passport/*`，页面为单页无框架实现（原生 JS + SSE），
沿用 `dsh-whale-widget` 已验证的安全实践：

- **信任栅栏**：Host 必须回环 / 显式声明、拒 `Sec-Fetch-Site: cross-site`、Origin 与 Host 同源；
  宿主 `connection.requestRejection` 可用时委托它，它抛异常按拒绝处理（fail-closed）。
- **写接口仅限本机**：所有 POST 必须来自回环地址，避免"能打开页面的人就能改配置"。
- 不引入构建链，`lib/panel/*.js` 直接作为静态资源下发。

面板分区：

| 分区 | 内容 |
| --- | --- |
| 设备 | 扫描/连接/断开、RSSI、电量、固件与协议版本、重连策略、"测试提示音" |
| 任务 | 与设备同源的列表、新建任务（选工作区 + 预设）、发送指令、中断、详情抽屉 |
| 审批 | 待审批队列、来源（网页/设备）、耗时、允许一次 / 拒绝 / 本会话总是允许 |
| 语音 | STT provider 状态与准备进度、模型下载、免确认开关、录音历史与重识别 |
| 余额 | 总余额/充值/赠送/今日已用、刷新间隔、曲线（本地留存） |
| 诊断 | 链路日志、帧统计、丢片率、重传次数、一键导出诊断包 |

同时注册 DSH 侧工具，让 **Agent 自己也能操作设备**：

- `ap_device_status` / `ap_device_notify` / `ap_device_ask`（在设备上弹确认，返回用户选择）
- `ap_task_list` / `ap_task_create` / `ap_task_prompt` / `ap_task_cancel`
- `ap_balance`

这样"让 DSH 在设备上问我一个问题"也成为一种能力，反向也通了。

## 8. 分阶段实施计划

每个阶段都有**可独立验证的产出**，不追求一次做完。

### 阶段 0 · 环境就绪（进行中）
- 安装 ESP-IDF 5.5.3 到 `~/esp/esp-idf-v5.5.3`（不覆盖任何已有安装），校验 commit `b31fcc7a…`
- 安装构建工具：`cmake`、`ninja`、`ccache`（走 Homebrew 或官方预编译包，不用 `sudo xcode-select`）
- 运行 `idf_tools.py install` 装工具链、首次 `./tools/validate.sh --static` 跑通
- 安装上游要求的 5 个 skill：`passport-develop` / `passport-setup` / `passport-build` /
  `passport-device-test` / `passport-debug`，并验证可用

**验收**：`idf.py --version` 输出 `ESP-IDF v5.5.3`；`./tools/validate.sh --static` 通过。

### 阶段 1 · DSH 插件骨架 + BLE 链路打通（无固件改动）
- 插件骨架：`apply()` 立即注册注入行/路由，服务依赖用 `root.inject([...], cb)` 局部等待
  （照抄 `dsh-whale-widget` 的教训：对象级 `inject` 会推迟整个 `apply()`，导致桌面端注入竞态）
- BLE transport 抽象 + `mock` 驱动（无需硬件即可联调）+ `noble` 驱动
- 协议编解码 + 单测（host 侧 Node 原生 `node:test`）
- 面板页面第一版：设备扫描/连接、实时原始报文监视

**验收**：`mock` 驱动下完整跑通握手与心跳；面板可见连接状态与报文流。

### 阶段 2 · 固件 BLE GATT 服务 + 最小设备 UI
- 新增 `app_link.c`：NimBLE Peripheral + 三条 characteristic + 帧收发 + 流控
- 新增 `app_ui.c`：连接状态页（显示广播名、已连接/未连接、协议版本、RSSI）
- 广播名 `FoloPassport-DSH` + Manufacturer Data
- 同步脚本把固件源码落到构建树，`validate.sh --firmware` 出合并镜像

**验收**：Mac 面板扫描到设备 → 连接 → 握手成功 → 双向心跳；设备屏幕显示"已连接"。
**真实硬件联机在这一阶段首次达成。**

### 阶段 3 · 任务域（新建/选择/状态/提醒）
- 插件：`bridge/session` + `bridge/watch` + `bridge/balance`
- 固件：`app_task.c` 任务台列表、详情页、完成提醒横幅 + 提示音 + 未读点
- 中文字体核对与真机显示验收

**验收**：在设备上新建任务并看到它进入 RUN；电脑端发起一轮对话，设备实时显示 step 与工具名；
任务结束时设备弹出提醒并响铃。

### 阶段 4 · 审批域
- 插件：`approval/request` 瀑布拦截 + 桌面通知兜底 + 面板审批队列
- 固件：审批页、倒计时、防误触二次确认、超时默认拒绝

**验收**：制造一个需要审批的工具调用，在设备上"允许一次"→ 任务继续；
在设备上"拒绝"或超时 → 任务收到拒绝且 DSH 侧有审计记录。

### 阶段 5 · 语音链路
- 启用 host 侧 STT（`speech-to-text` + `sensevoice` 两个包），面板展示模型准备进度
- 固件：`app_voice.c` 录音 + ADPCM + 分包；录音页 UI
- 插件：`bridge/voice` 重组 + 识别 + 回显 + 注入

**验收**：对着设备说"帮我把 README 的错别字改一下"，设备显示识别文本，
确认后任务收到该指令并开始执行。

### 阶段 6 · 打磨与交付
- 断线重连、低电量策略、任务数上限分页、错误态全覆盖
- `docs/04-验收清单.md` 逐项打勾；`validate.sh` 完整门禁
- 交付：合并固件 `build/FoloToy-AI-Passport-full.bin` + 插件包 + 文档
- 按上游规范报告四项状态：`Build` / `Host tests` / `Device tests` / `Unverified`

## 9. 风险与对策

| # | 风险 | 影响 | 对策 |
| --- | --- | --- | --- |
| R1 | **noble 原生模块与 DSH 内置 Node 24 的 ABI 兼容** | BLE 完全不可用 | transport 三层抽象（`noble` / 外部 BLE 桥进程 / Swift CoreBluetooth 助手），任一路径通了即可；阶段 1 就验证，不拖到最后 |
| R2 | macOS 蓝牙权限（TCC） | 首次调用被静默拒绝 | `Info.plist` 已含 `NSBluetoothAlwaysUsageDescription`（**已实测确认**）；仍要在面板显式展示"蓝牙权限被拒"并提供跳转系统设置指引 |
| R3 | BLE 实测吞吐/丢包不足 | 语音卡顿、状态延迟 | ADPCM 4:1 压缩、音频通道不重传、采样率可降级到 8 kHz；真机实测丢片率作为阶段 5 的门槛 |
| R4 | 中文字形缺失 | 界面中文显示成方框 | 按上游字体检查清单先核对字形覆盖与控件字体，真机截图验收；不通过不进入下一阶段 |
| R5 | ESP32-C3 单核、Wi-Fi/BLE 共存内存紧张 | BLE + 音频 + UI 同跑时 OOM 或看门狗复位 | 不启用 Wi-Fi；音频 DMA 缓冲有界；NimBLE 栈与 LVGL 任务优先级明确；连续录音时长上限 15s；实测内部 RAM 水位 |
| R6 | SenseVoice 模型 239 MB 下载慢或失败 | 语音功能不可用 | 面板提供镜像源选择与断点续传状态；失败时明确报错并保留已完成文件；语音以外的功能不受影响 |
| R7 | 审批在设备上误触放行 | 安全风险 | 高风险工具默认停在"拒绝"；二次确认；倒计时超时拒绝；DSH 侧完整审计；可选"设备审批上限"（如只允许只读工具在设备上批） |
| R8 | `sessionController.prompt` 的 `requestId` 需唯一 | 指令被拒或重复 | 插件侧用 ULID 生成并去重；失败重试幂等 |
| R9 | 上游 `vendor/ai-passport` 后续更新与本地改动冲突 | 升级困难 | 我们的固件代码全部是**新增文件**，只对 `main/CMakeLists.txt` / `main.c` 做最小侵入式改动并记录补丁点；`firmware/` 保留权威副本便于 rebase |
| R10 | 设备在无人值守时被他人取走 | 数据泄露 | 任务标题与摘要可脱敏（面板开关）；审批可在设备侧全局关闭（只允许电脑批）；断开即清屏 |

## 10. 待确认事项

1. **BLE 驱动优先级**：默认按 `noble` → 外部桥进程 → Swift 助手的顺序尝试。若你希望直接用
   Swift/CoreBluetooth 助手（更稳定但要额外维护一个二进制），请告知。
2. **面板是否需要"设备审批"总开关之外的策略**：例如只允许在设备上批只读工具（`read`/`glob`/`grep`），
   写操作一律回电脑批。安全默认值我倾向"允许"，你若要更严可以改。
3. **任务标题脱敏**：设备在公共场合可能被旁人看到任务标题。是否需要默认只显示序号 + 状态？
4. **语音免确认**：识别完直接下发，还是必须在设备上按确定确认一次？我默认**要确认**（防误识别）。

以上 4 点不影响阶段 0～2 开工，可在对应阶段前给结论。
