# 5 · 语音发送：设备侧设计（app_voice）

> 状态：**方案参考同类项目后修订中**。主机侧 `lib/bridge/voice.js` 已完整实现
> （收流→重组→解码→识别→回发）。本文件定义**设备侧唯一缺失的部分**。

## 0. 参考同类项目（folotoy 生态）

调研了官网 https://ai-passport.folotoy.cn 及两个同类项目，对本设计有直接影响：

### 参考 A：`zhaohuaxiaoy/folo-ai-passport-voice`（最相关）
同为 ESP32-C3 + AI Passport，**已真机验证的"按住说话→桌面输入框"语音输入**。关键做法：

| 维度 | 参考做法 | 对本设计的影响 |
|---|---|---|
| **传输** | **流式**：录音时**边录边发**，3200B/100ms 帧经 BLE GATT NOTIFY 连续上行 | ★ **绕开了我们的 2048B/0.26s 瓶颈** —— 不攒 15s 再发 59 条，而是边录边发 |
| **内存** | 静态环形缓冲、**源端丢帧**不整段缓存、掉帧对账（400KB SRAM 装不下整段录音） | 与 §3 结论一致：设备**不能**缓冲整段录音 |
| **触发** | **按住说话 PTT**：按下即录（滴声），松手自动发送；<500ms 误碰丢弃 | ★ 按键有 press/release（见下） |
| **按键语义** | 用 `iot_button`；**"单击+长按"同键互斥**（判成长按就不补报单击） | 长按阈值 500ms |
| **识别** | 火山流式 ASR，partial 实时回显，松手定稿注入 | 我们走 DSH `ctx.speechToText`（离线 SenseVoice） |
| **状态机** | HOME→READY→LISTENING→TRANSCRIBING→…，纯 C 归约器 + host 测试 | 可借鉴：录音态可视化 |
| **UI** | LISTENING 页：麦克风图标 + 计时 | 我们范围 C 暂不做录音页 |

### 参考 B：`FoloToy/ai-passport`（上游基线）
- `docs/reference/shinku-chen/voice-keychain` 是**音频播放**（Opus 解码回放），非录音输入，**不适用**
- 上游 `main` 是硬件测试基线，无语音输入实现

### ★ 对本设计的三个关键修正

1. **传输从"攒够再发"改为"流式边录边发"**（参考 A）：
   - 我原方案：录满 → 分 59 条消息发 → 撞上 2048B 载荷上限 + 主机拼接难题（§3）
   - 参考方案：录音过程中持续发帧，每帧是独立小消息（<2048B），主机按到达顺序接
   - **仍然需要改主机 `voice.js`**（现在是"voice.end 后一次性解码"，流式要边收边解或 end 时按到达序拼），但**避开了单消息 0.26s 的硬上限**

2. **触发方式**：参考 A 证明按住说话（PTT）可行 —— 但需确认它的**按键驱动是否提供 release 事件**。
   若提供，可从"长按确定=录音"改为"按住确定=录音（松开结束）"，体验更自然。

3. **内存**：必须静态环形缓冲 + 源端丢帧，**不能**缓冲整段（与 §3.1 一致）。

## 2. 音频与编码（与主机严格一致）

- 采集：`bsp_audio_set_format(16000, 16, 1)` → `bsp_audio_read` 循环 20ms 块（320 样本 / 640B）
- 编码：**IMA/DVI ADPCM 4:1**，压缩后 16k/16bit/mono 从 32KB/s → 8KB/s
- **块格式（必须与主机 `decodeImaAdpcm` 字节一致）**：
  ```
  [4 字节块头] predictor=int16 LE | stepIndex=uint8 | 保留=uint8(0)
  [数据]       每字节 2 个 4bit 采样，**低 nibble 先**
  ```
  单块数据 504B → 1008 采样（63ms）。主机解码按 `min(剩余, 504)` 容错块边界，
  但每块**自带块头**，设备必须每 504B 数据就写一个新块头。
- **步长/索引表**：`IMA_STEP_TABLE`（89 项）、`IMA_INDEX_TABLE`（16 项）
  必须与 `voice.js` 第 270 行起的两张表**逐字节相同**，索引更新顺序相同 —— 否则解出来是噪声。
  实现时把这两张表从 `voice.js` 原样抄成 C 数组，不"优化"。

## 3. 分片与会话（★ 已核对代码，结论修正）

### 3.1 真实瓶颈不是 seq 位宽，是单消息载荷上限

核对 `app_link.c` / `app_proto.h` / `voice.js` 后确认：

- `ap_link_send_voice()` **每次调用都把 seq 从 0 开始**（`for seq=0..total`），调用间不携带状态
- 主机 `#onVoiceBytes` 按 `msgId(=sessionId)` 归组、按 `seq` **去重**（`session.chunks.has(seq)`）
- 主机 `assembleWav` 要求 seq **从 0 连续**（`for seq=0..highest`），且丢片率 ≤15%
- **`seq` 是 4 bit（0~15）**；但**单消息载荷上限 `AP_MAX_PAYLOAD_BYTES=2048`** 才是硬瓶颈：
  2048B ÷ 8000B/s(ADPCM) = **0.26 秒/条消息**（4bit 的 16 片 = 3904B 反而超过 2048 上限，用不满）

### 3.2 推论：扩 seq 位宽**没有用**

15s 录音 = 120KB 压缩 = **约 59 条消息**（每条 2048B）。无论 seq 扩到多少位，
单条消息都卡在 2048B 载荷上限 → 撑死 0.26s。**唯一可行路径是"多条消息 + 主机按到达顺序拼"**。

### 3.3 因此必须改主机（方案 A1，已确认方向）

当前主机按"单 sessionId + seq 0..N 去重"建模，**装不下跨消息的录音**。改法：

- `#onVoiceBytes`：不再用 4bit seq 去重，改为**按消息到达顺序追加**（或用 FIRST/LAST flag 判断段边界，主机把同一 sessionId 的多段 payload 顺序拼接）
- 单条消息内 seq 仍用于片内排序（16 片内连续），**跨消息由主机累加偏移**
- `assembleWav` 改为对"拼接后的连续字节流"做 ADPCM 解码

设备侧：一条录音 = N 次 `ap_link_send_voice(msg_id=sessionId, ...)`，
每次都是 seq 0..total-1（片内连续），主机按到达顺序拼。

> 备选（不动主机）：把录音切成独立 sessionId 分段识别 → 会得到多条文本，**不成立**（语音是一句话）。

### 3.4 会话约定

- `voice.begin { sessionId, sampleRate:16000, bits:16, channels:1, codec:'ima-adpcm' }`，sessionId 取 4bit 内一个值（如 1）
- 整段录音所有消息**复用同一 sessionId**；主机靠到达顺序拼
- `voice.end { sessionId }` 收尾


## 4. `app_voice.h` 接口（草案）

```c
// 录音状态
typedef enum { AP_VOICE_IDLE, AP_VOICE_RECORDING, AP_VOICE_SENDING } ap_voice_state_t;

// 初始化（建任务/队列）。失败不致命。
esp_err_t app_voice_init(void);

// 长按触发：开始录音；松手调 app_voice_stop()。返回是否成功启动。
bool app_voice_start(void);
// 松手：结束采集 → 编码余量 → 发 voice.end。IDLE 时无副作用。
void app_voice_stop(void);

// 是否在录音中（按键/熄屏判断用）
bool app_voice_recording(void);

// 主机回的 voice.result/error → 反馈（toast 或录音页）。由 app.c 收到消息时调用。
void app_voice_on_result(const char *text);
void app_voice_on_error(const char *err);
```

线程模型（照抄 app_alert 的成熟模式）：
- 采集在**独立任务** `app_voice_task`（`bsp_audio_read` 阻塞，不能放 LVGL 任务）
- `app_voice_start/stop` 由**按键上下文**调用，只发信号给任务（不直接碰音频/LVGL）
- 结果反馈走 `app_ui_post_toast`（线程安全的投递），不直接碰 LVGL

## 5. 触发与反馈（✅ 最终决策）

- **触发 = PTT 按住说话**：按住确定键开始录音，松开自动结束并发送。
  - 需在 **BSP 加注册 `BUTTON_PRESS_UP`**（`iot_button` 支持，我们当前没注册它）。
  - 区分：`PRESS_DOWN`（若已在录音则忽略/或作为取消）→ 录音；`PRESS_UP` → 结束。
  - **保持按下**期间录音；`LONG_PRESS_START` 不再用于录音（避免与 PTT 冲突）。
  - **断开连接从设备端移除** —— 断开只由插件/控制面板控制。已删 `ap_link_disconnect_peer()` 调用。
- **录音上限 15s**：到点自动结束（VAD 静音 1.2s 也自动结束，二者先到为准）。
- **状态反馈 = 只用 toast**（最小改动，不做录音页）：
  - 开始录音 → toast「开始说话」（或「录音中」）
  - 结束/识别中 → toast「识别中…」
  - 结果 → toast 识别文本；失败 → toast 错误
  - （完整录音页的实时电平/计时/动画，范围 C 后续再加）

## 6. 决策点（✅ 全部已定）

**A. 传输方式** → **流式边录边发**（参考 `zhaohuaxiaoy/folo-ai-passport-voice`），绕开
   `AP_MAX_PAYLOAD_BYTES=2048`（0.26s/条）的硬上限。每帧是独立小消息（<2048B），
   主机按到达顺序拼接。**仍需改主机 `voice.js`**（§3.3）。

**B. 录音触发键** → **PTT 按住确定说话，松开发送**（BSP 加 `PRESS_UP`）。断开移到插件端。

**C. 范围** → 核心链路 + **toast 状态反馈**（15s 上限），不做录音页 UI。

**D. 端到端验证** → 需启用 SenseVoice（识别引擎）+ 真机录音。
   分两步验证：①设备录音/上行/主机拼接解码（不需要 SenseVoice，看字节日志）
   ②音频→文本→注入（需要 SenseVoice，239MB 模型下载）。

**E. 录音上限** → **15s**（流式后这个数字不影响分包，纯时长偏好）。

## 8. 风险

- **两张 ADPCM 表不一致** → 解码出噪声（最隐蔽，靠真机听/看识别结果才发现）
- **流式拼接改错** → 音频错位/丢段（§3.3 改主机是关键路径，靠单元测试 + 真机验证）
- **BSP 加 PRESS_UP** → 若与现有 click/long 判定冲突（参考项目提到 iot_button 互斥语义），需真机验按键

## 9. 真机返工记录（两个已修复的缺陷）

### 缺陷 A：设备先提示"识别失败"，之后才出识别文字

**现象**：按住说话松手后，设备屏幕先弹一条红色"识别失败"toast（4 秒），
之后才轮到"识别中…"和识别文字的 toast —— 但识别本身是成功的，文字也出来了。

**根因**（`vendor/ai-passport/main/app_voice.c`）：采集循环里
`bsp_audio_read()` 返回非 `ESP_OK`（流末尾一次正常 EOF/短暂 IO 抖动）时，
旧代码立刻 `app_ui_post_toast("音频读取失败…", true)` 弹一条**紧急** toast。
而 urgent toast 的显示时长是 4000ms，非 urgent 是 2500ms ——
这条"失败"toast 把随后才轮到的"识别中…/识别结果"toast **盖住或排到了后面**。
实际上此刻缓冲里已经有大半段可识别的音频，主机照样识别出了文字。

**修法**：
- 采集循环读不到样本时**不再 toast**，改为安静收尾（`ESP_LOGI` 记日志即可），
  把已编码的音频照常发 `voice.end` 让主机识别；
- 收尾处增加判断：只有"整段一个有效样本都没采到"（`s_read_count == 0`）
  才提示真正的录音失败"录音失败：没采到声音"；
- 只要采到过样本就走"识别中…"，让主机的识别结果说话。

**结果**：toast 顺序变成 `识别中…` → `识别文字`，不再有前置的误报"失败"。

### 缺陷 B：显示的文字不全，混有方块（tofu）

**现象**：识别结果/任务标题显示不全，部分汉字位置显示成方块（□）。

**根因**（两个叠加）：

1. **字体子集覆盖面不足**。`tools/make-fonts.py` 的 `collect_rendered_chars()`
   只扫描 `vendor/ai-passport/main/app*.c` 的**源码字符串字面量**（约 350 个汉字），
   生成的 `app_ui_font_cjk.c` 子集完全覆盖这些静态文案。但设备上真正显示的
   **识别结果**（`voice.result` 的 text）、**任务标题**（`task.state` 的 title）、
   **主机错误信息**（`voice.error` 的 message）都是**运行期动态字符串**，
   字符集是"全部常用汉字"，远超这 350 个。落在这 350 字之外的汉字，
   LVGL 找不到字形就渲染成方块。

2. **toast 缓冲区太小 + 按字节硬截断**。`app.c` 的 `char text[120]`、
   `app_ui.c` 的 `s_pending_toast[80]`、`toast_show` 的 `clean[80]` 都是小缓冲，
   `snprintf("%s")` 按**字节**截断 —— UTF-8 汉字 3 字节，按字节切会切在汉字中间，
   产生非法 UTF-8 字节序列，LVGL 渲染成**半截字/方块**。

**修法**：

1. **字形子集扩容**（`tools/make-fonts.py`）：新增 `COMMON_CJK` =
   GB2312 一级汉字（3755 字，覆盖 99% 日常用字），无条件纳入子集。
   代价：20px 中文字体从 252KB 涨到 2.65MB，但 factory 分区 7.9MB、
   当前固件 1.4MB，仍有 4MB+ 余量。权衡同源：
   **多收字形只是多占 flash，漏收一个字就是屏幕上出现方块**。

2. **UTF-8 安全截断**（新增 `main/utf8_clamp.c/h` + host 测试
   `tests/test_utf8_clamp.c`）：`utf8_copy_clamped()` 保证截断永远落在
   **UTF-8 字符边界**上，不会留下半截汉字。`app_ui.c` 的 toast 路径
   （`app_ui_post_toast` + `toast_show`）全部改用它；`app.c` 的
   `voice.result`/`voice.error` 缓冲扩到 512/256 字节。

**结果**：识别结果/任务标题等动态文本不再出方块、不再被截成半截乱码。

**防回归**：`tools/make-fonts.py --check` 现在会校验 GB2312 一级汉字
100% 被字形覆盖（不只校验静态文案）；`tools/validate.sh --static` 里
新增 `test_utf8_clamp` host 测试，锁住 UTF-8 边界截断行为。
