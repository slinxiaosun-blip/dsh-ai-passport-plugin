## 2 · 运行计时设计

### 2.1 语义定义（先定清楚，再写代码）

| 问题 | 决定 | 理由 |
| --- | --- | --- |
| 计的是什么 | **当前这轮忙碌已持续的墙钟时间** | 用户问的是「它跑了多久」，不是「CPU 干了多久」 |
| 多会话并行 | 取**最早开始**的那个会话起算 | 单会话时即该任务时长；多会话时表达「这轮忙了多久」，与状态卡标题「N 个任务执行中」一致 |
| 审批等待算不算 | **算**（锚点不重置），但**待审批页不显示计时** | 审批仍属于同一个任务在占用用户；但待审批时该显示的是「等你决定」 |
| 已完成状态 | 不显示 | 完成态只停留 8 秒，显示计时会让人以为还在跑 |
| 精度 | 秒级（`MM:SS`，≥1 小时转 `H:MM:SS`） | 小屏不显示毫秒；等宽数字避免每秒抖动 |
| 起点未知时 | **不显示计时**（主机不下发 `elapsedMs`） | 插件中途启动/设备中途连上时，起点是「首次观察」而非真实开始，算出来的数会系统性偏小。设计稿要求计时只显示纯 `MM:SS` / `H:MM:SS`（不加 `~`、`≥` 之类前缀），也就没有任何位置标注「这是近似值」—— 与其给一个精确到秒却偏小的数字，不如空着（会撒谎的指示器比没有更糟） |

### 2.2 数据流：主机播种 + 设备走秒

```
主机（插件）                               设备（固件）
─────────────────────────────────────────────────────────────
turn/start ──► runStarts.set(sessionId, t0)
                    │
                    ├─ elapsedMs = now - min(runStarts.values())
                    │
task.state {state, title, elapsedMs, sinceReliable}
        ───────── BLE（仅状态变化/重连时）─────────►
                                              ① 收到 elapsedMs → 记锚点
                                              ② LVGL 定时器每秒 +1
                                              ③ 渲染 01:23
```

**为什么不让主机每秒推一次**：`docs/02` 已记录「每次工具调用都推一条导致 BLE 流量偏高」的教训；每秒推送是同一类错误的极端版。设备有单调时钟，走秒是它最擅长的事；主机只需在**状态变化**与**链路就绪**这两个时刻给出真值。

**为什么不用设备墙钟对齐**：设备没有 RTC，也没有必要。传「已运行毫秒数」而不是「开始时间戳」，天然免疫时钟不同步。

### 2.3 协议增量（附加字段，不升版本）

`task.state` 增加两个**可选**字段，`PROTOCOL_VERSION` 保持 `1`：

| 字段 | 类型 | 含义 | 缺省行为 |
| --- | --- | --- | --- |
| `elapsedMs` | number | 该轮忙碌已运行毫秒数（主机在发送时刻计算） | 设备不显示计时 |
| `sinceReliable` | boolean | 起点是否为真实 `turn/start` | **目前恒为 `true`**：起点不可靠时主机不下发 `elapsedMs`（见 §2.1）。字段留给链路日志与其它客户端 |
| `hostEpochSec` | number | 主机墙钟：UTC 秒 | 设备状态条显示 `--:--` |
| `hostTzOffsetMin` | number | 主机时区偏移，分钟，东正西负（北京 `+480`） | 同上；**两个字段必须成对**，只有 epoch 会显示成 UTC（差 8 小时的"看起来对"最坏） |

> 时钟为什么发「UTC 秒 + 偏移」而不是格式化好的 `"20:17"`：设备要自己走秒，
> 一串定死的字符过几分钟就是错的。发种子，设备就能一直算下去。
> 为什么是**秒**不是毫秒：固件侧 `long` 在 ESP32-C3 上只有 32 位，毫秒级 epoch 直接溢出。

```json
{ "type": "task.state", "state": "running", "title": "2 个任务执行中",
  "elapsedMs": 83400, "sinceReliable": true }
```

**兼容矩阵**（这是「不升版本」的价值：过渡期任何一种组合都不会变砖）：

| 固件 \ 插件 | 旧插件（无字段） | 新插件（带字段） |
| --- | --- | --- |
| 旧固件 | 现状 | 正常，只是**不显示计时**（多余字段被忽略） |
| 新固件 | 正常，**不显示计时** | ✅ 完整功能 |

> 与 `PROTOCOL_VERSION` 的关系：版本号语义是「不兼容变更」。加可选字段属于兼容变更，若强行升到 2，会让「新固件 + 旧插件」直接报版本不一致而拒绝工作——为了一个显示功能把可用组合砍掉一半，不值得。

### 2.4 主机侧改动

### 2.6 边界行为（逐条验收）

| 场景 | 期望 |
| --- | --- |
| 正常跑 10 分钟 | 误差 ≤ 1 秒（与电脑秒表对比） |
| 设备熄屏 3 分钟再亮 | 时间**不跳、不漂**（重算自单调锚点，不是累加） |
| 掉线 1 分钟再连 | 由主机 `elapsedMs` 重新播种，**不归零** |
| 设备重启（运行中） | 重连后按主机值继续；主机若也不知道起点 → **不显示计时** |
| 任务 A 跑 2 分钟后 B 开始 | 计时**不重置**（取最早开始） |
| 运行 → 待审批 → 运行 | 计时**连续**（锚点不重置），待审批期间不显示 |
| 运行 → 已完成 | 计时消失 |
| 按住说话 | 计时不刷新（状态推送被抑制），松手后恢复正确值 |
| 插件中途启动 | 起点不可靠 → 主机不下发 `elapsedMs`，设备**不显示计时**；下一次 `turn/start` 起恢复 |
| 跨 1 小时 | 自动切 `H:MM:SS`，无截断 |

### 2.7 状态条时钟（10-31 追加）

用户要求：**电量左边显示当前系统时间**；同时明确「空闲时不显示（运行）时间」，
即运行计时只在「运行中」出现，时钟则常驻。

**横排预算**（安全区 220，全部来自 `app_ui_theme.h` 的宏，`verify-layout.py` 直接解析）：

| 元素 | x 范围 | 字号 | 说明 |
| --- | --- | --- | --- |
| 信号格 4 格 | 0 .. 18 | — | 宽 3 / 间距 5，圆端 |
| 应用名 | 25 .. 98 | 16px | 「AI 通行证」实宽 65.8，框宽 73 |
| **当前时间** | **102 .. 144** | **16px** | `HH:MM`，右对齐，框宽 42 |
| 电量百分比 | 150 .. 194 | 16px | `100%`，右对齐，框宽 44 |
| 电池外壳 | 198 .. 220 | — | 20 + 2px 正极凸起 |

**四个元素统一 16px 思源黑体**（`UI_FONT_CJK16`）。原先应用名 16px、时间与电量 8px 点阵，
用户看到的正是「大小不统一、没对齐」。

> ⚠️ 这里记一次**算错**的教训。我曾断言「220px 放不下全 16px，要 250px，必须缩文案」，
> 并据此让用户在三个方案里选了「缩文案」。错在拿**等宽点阵**的度量（Press Start 2P 在 16px 下
> 每字符前进 16px：`20:17`=80、`100%`=64）去估**比例字体**。
> 思源黑体 16px 的数字前进 8.81、冒号 4.31、百分号 14.63 →
> `20:17` 只有 39.6、`100%` 只有 41.1，四个元素合计 186px，**一个字都不用缩**。
> 判字宽只能读生成字体的真实 `adv_w`（`tools/verify-layout.py` 的 `text_width`）。

**为什么不做成「主机推字符串」**：设备要自己走秒，推一次字符串过几分钟就是错的。
做法与运行计时同源 —— 主机发 `hostEpochSec` + `hostTzOffsetMin` 做种子，
设备记锚点、用 `esp_timer` 本地推进，**每分钟重算一次**并只在分钟变化时重设文本。

**未收到种子时显示 `--:--`**：与电量的 `--` 是同一种"我还不知道"的表达。
两个标签都是**固定框宽 + 右对齐**，种子到达后只是左边缘生长，不牵动右侧电量与外壳。

**换算放在纯逻辑里**（`main/app_clock_logic.c`）：`ap_clock_hhmm(epoch_sec, tz_min, &hh, &mm)`。
跨日取模、半小时时区（`+330`）、负偏移回绕这些边界全在宿主测试
`tests/test_app_clock.c` 里钉住 —— 这类错在真机上表现为"差 8 小时"，
盯一天都不一定发现，一行断言就够。

**运行计时与时钟的关系**：两者互不干扰。计时只在 `RUNNING` 出现、离开即清空
（`refresh_timer` 现在**每次读标签实际内容**再决定要不要清，不再靠标记位，
免得任何一处漏更新在空闲界面上留一个过期数字）；时钟在所有状态都显示。

### 2.8 状态词只能出现一次（10-31 追加）

用户反馈「状态界面上状态显示有重复的」。根因在 `refresh_state()`：它把
`state_style()` 返回的**同一个字符串**分别塞给了大字和徽章文字，于是

```
[● 运行中]          00:12     ← 徽章：圆点 + 状态词
运行中                         ← XL 大字：同一个词
没有正在执行的任务                ← 提示行：同一件事换个说法
```

同一句信息说了三遍。状态是"一眼"信息，重复不是强调，是噪音。

现在的分工：

| 元素 | 承担什么 | 说明 |
| --- | --- | --- |
| 状态灯 | **只用颜色**表达状态 | 22×22 正圆，12% 淡底 + 5px 实色芯；`state_chip_bg()` 出底色、`state_style()` 出色 |
| XL 大字 | **唯一的状态词** | 「空闲 / 运行中 / 待审批 / 已完成」只在这里 |
| 提示行 | **只放主机下发的任务标题** | 没有标题就空着，不再复述状态 |
| 计时 | 运行时长 | 仅 `RUNNING` 时有内容 |

所以 `state_style()` 的 `hint` 现在四个状态全为空字符串，函数保留这个出参是为了
不改调用签名；真要加"解释性副标题"时往这里加，而不是在 `refresh_state` 里另写一份。

**验收**：任一状态下，屏幕上同一状态词只能数出一次。

### A.1 验证中发现并修复的缺陷

**`BridgeProcessTransport.doDispose()` 永不 resolve**，导致 `bridge-process.test.js` 的 11 条用例变成 cancelled（不是 fail，更容易被忽略）。

- **根因**：`doDispose()` 里 `await sleep(60)`，而 `sleep()` 把定时器 `unref()` 了。事件循环里只剩这一个（被 unref 的）定时器时，循环直接判空——Promise 永远不 settle。node --test 报 `Promise resolution is still pending but the event loop has already resolved`。
- **影响面**：`dispose()` 在插件卸载/退出时被调用，真实环境下事件循环通常还有别的任务，所以**平时不显形**；但它是一个真实的挂起风险，也让测试基线带 11 条噪音。
- **修复**：`lib/ble/bridge-process.js` 的 `sleep()` 去掉 `unref()`（50/60ms 的定时器不可能拖住进程退出），并补注释说明为什么不能 unref。
- **回归**：`bridge-process.test.js` 13/13 通过；全量 168/168、0 failed、0 cancelled。

### A.2 文档修正

`docs/04` §7.4 原先让人 `curl http://127.0.0.1:19387/...`，但**端口是动态分配的**（两次实测分别是 55609 / 55924）。已改为「先查 host 进程端口再 curl」，并补上 `--noproxy '*'`（本机代理会把 127.0.0.1 也拦成 502，这个坑实测踩到了）。

| --- | --- |
| 13:46:17.532 | `turn/end` |
| 13:46:17.541 | `status:idle`（9ms 后配对到达） |
| 13:46:25.585 | 状态回落 `idle`（即「已完成」停留 8.05s） |

错因不在 DSH，在观测窗口：**`stateTrace` 当时只保留 12 条**。一轮任务里
step/tool/job 能刷几十条，12 条连半个轮次都装不下；我看的时候任务还没结束，
`turn/end` 根本没发生，环里当然只有中间那些事件。
**环形缓冲的窗口长度会伪造出「事件不存在」这种结论** —— 这比漏看更危险，
因为它看上去像实证。

已做的三处修正：

1. `TRACE_LIMIT` 12 → **40**，够装一整轮；
2. 新增 `turnTrace`（**只**记 `turn/start` / `turn/end` / `status:run` / `status:idle`，
   上限 20 条），边界不再被噪音淹没，看一条链就知道起点从哪来、结束判没判；
3. `state.test.js` 加一条用例，用 30 条 `tool/call` 冲环，断言 `turnTrace`
   仍只有 3 条边界 —— 把这个坑本身钉进测试。

### B.8.2 修正后的事实（以实测为准）

| 方案原文 | 实际 |
| --- | --- |
| `turn/end` 删除起点并进「已完成」 | **成立**。13:46:17.532 实测收到，8.05s 后回空闲 |
| `turn/start` 播种可靠起点 | ~~本轮窗口未捕获到~~ → **10-31 20:08 实测捕获，且只比 `status:run` 晚 4ms**（见 §B.9）。两条路都接：有 `turn/start` → `reliable=true`；只有 `status(true)` → 记不可靠起点，**且不下发 `elapsedMs`**（设备不显示计时） |
| 可靠时显示 `MM:SS`，否则 `~MM:SS` | **已废弃**。设计稿要求纯格式，`~` 去掉；起点不可靠时改为不显示计时（§2.1） |

结束判定保留双路兜底（谁先到谁算）：`turn/end` 立即结束；没有它时靠
`api-session/status` 的 `false` + 1200ms 窗口吸收工具调用之间的闪断。

**推送模型**：主机在起点推一次种子 `elapsedMs`，之后设备用 `esp_timer`
本地走秒。因此主机快照里的 `elapsedMs` 是**种子**不是实时值（任务开始后
`api-session/status` 不再重发）；空闲时快照干脆不含该字段。
面板若要显示"正在走"的数字，应自己按种子 + 本地差值插值，而不是直接读快照。

**排障抓手**：`/dsh-passport/state.json` 现含 `stateTrace`（40 条原始事件）
与 `turnTrace`（20 条边界），配合 `/dsh-passport/action`（POST，如 `pair.unpair`），
可在不重启、不读串口的前提下定位主机侧问题。

**桌面端入口**：DSH 桌面版的 webServer 端口是**动态**的，不在 3080。
用 `lsof -nP -a -p <DeepSeek Harness 主进程 PID> -iTCP -sTCP:LISTEN` 取实际端口
（本次为 `127.0.0.1:65513`，重载后变成 `127.0.0.1:64772`），别拿 web 版的 3080 去试。

### B.9 P4 真机验证：计时格式与完整生命周期（10-31 20:08 ~ 20:11）

**固件**：`FoloToy-AI-Passport-full.bin`（1 820 992 字节，SHA-256 `b06de76a…`）
写 `0x0`，Hash 校验通过，硬复位后重连 `handshake=true`、MTU 250、RSSI −50。

**主机侧抓到的一整轮**（`state.json` 轮询，250ms）：

```
20:08:15.310  status:run      ┐
20:08:15.314  turn/start      ┘ 相隔 4ms
20:08:15.314  taskState=running  elapsedMs=4  sinceReliable=True
20:10:46.987  turn/end          ← 本轮实际跑了 151.7 秒
20:10:46.989  status:idle       ← 2ms 后配对到达
20:10:55.039  回落 idle         ← 「已完成」停留 8.05 秒，与 COMPLETED_LINGER_MS 一致
```

**两条结论**：

1. **`turn/start` 确实会到，而且几乎与 `status:run` 同时（4ms）**。
   §B.8.2 那句「本轮窗口未捕获到」是因为看的时机落在轮次中段，不是事件不存在。
   顺便解开了更早那个谜：设备当时一直显示 `~`，**不是**因为拿不到可靠起点，
   而是「`status:run` 先推一次无种子 → `turn/start` 补种子」这两次推送
   落在同一秒、去重键相同，被 `push()` 合并掉了。现在的去重键在无种子时
   不带秒数（`running|标题`），补种子后变成 `running|标题|秒`，两者必然不同，
   所以这次升级推送一定能发出去。
2. **设备显示符合设计稿**：右上角是纯 `MM:SS`，正常逐秒推进，
   与主机侧算出的值同量级，未与左侧徽章重叠。

**结束路径**：`turn/end` 立即结束（2ms 后 `status:idle` 跟着到），
「已完成」停留 8.05 秒后回落空闲；此时设备上的计时标签被清空（状态离开运行中即清）。

**遗留未测**：熄屏 3 分钟不漂移、掉线重连不归零、双任务取最早、跨小时 `H:MM:SS`
（需要更长的任务或制造断链，见 §2.6 清单）。

### B.10 串口截屏在本版控制台下失效（未修，不影响计时）

**症状**：`tools/screenshot.py -p /dev/cu.usbmodem2201` 发 `FAP_SCREENSHOT_V1\n` 后
等不到应答头；手工发命令再读串口，日志里连 `命令命中，开始截屏` 都不出现——
说明设备的读任务根本没读到这几个字节，不是"读到了但渲染失败"。

**已知事实**：

| 项 | 值 |
| --- | --- |
| `CONFIG_APP_ENABLE_SCREENSHOT` | `y`（功能被编进去了） |
| `CONFIG_ESP_CONSOLE_USB_SERIAL_JTAG` | `y`（控制台与截屏抢同一条 USB-Serial-JTAG） |
| `app_screenshot_start()` | 在 `app.c:865` 被调用；失败只打一条 `串口截屏未启用` 的 warning |
| 串口本身 | 正常，能读到 NimBLE/`app_main` 日志 |

**最可能的原因**（按可能性排序，都还没验证）：

1. `usb_serial_jtag_driver_install()` 失败（console 已经占着这条流），
   于是 `shot_task` 压根没创建 —— 启动日志里应有 `USB 串口驱动安装失败` 的 warning，
   但那是开机瞬间打的，错过了。
2. `lv_draw_buf_init()` 失败（整屏 150KB 静态缓冲与 LVGL 内存池的取舍，见该文件头）。
3. 驱动装上了，但 `usb_serial_jtag_vfs_use_driver()` 之后控制台与读任务仍在抢。

**复现启动日志的正确姿势**：需要拉 RTS 复位。注意 `/dev/cu.*` **不支持**
`TIOCMBIS/TIOCMBIC`（实测 `Errno 25 Inappropriate ioctl for device`），
要用 `/dev/tty.usbmodem2201`，或者干脆用 `esptool --after hard_reset`。

**影响**：无法自动截图做像素比对，UI 验收暂时只能靠人眼看屏幕。
计时功能的验证不依赖它。

### C.2 七个"故意不照设计稿做"的地方

设计稿是按 11px 西文的近似画的，真机字体粒度比它粗。以下每处都写了原因，改回去之前先读：

| 设计稿 | 实做 | 原因 |
| --- | --- | --- |
| 徽章高 18px | **22×22 圆灯，不带文字** | ① 18px 是按 11px 西文算的，设备上中文最小 16px（行高 20），装进去会裁字 → 方块；② 设计稿的徽章里写着状态词，而大字也写同一个词，屏幕上每个状态出现两次（10-31 用户反馈「状态显示有重复」），所以徽章退化成纯色灯 |
| 计时 15px | **16px 思源，恒不降级** | 旧实现跨 1 小时降 8px，理由是按**点阵**算 `10:23:45` 要 128px；思源下只有 61.5px，降级已删（10-31） |
| 电量百分比在图标右 | **在图标左** | `100%` 需 32px，放右侧会溢出 220 安全区 |
| Toast 全屏遮罩 | **不做遮罩** | 全屏半透明触发整屏重绘（掉帧）；且 Toast 是通知不是模态，遮罩会误导 |
| 审批按钮 44px 药丸 | **30px R10 行卡** | 与追问/设置行统一几何；改 44 会破纵向预算 |
| 配对码 XL 40px | **20px** | 6 位码在 40px 下宽 240px > 220，装不下 |
| 状态卡随状态变色 | **底色固定，颜色只给状态灯 + 大字** | 整块 182px 铺 20% 状态色时，待审批半屏发黄、字压在上面难读 |
| 提示行复述状态 | **只显示主机下发的任务标题，没标题就空着** | 原来空闲时写「没有正在执行的任务」、运行中写「任务正在执行」，都与大字同义，属重复 |
